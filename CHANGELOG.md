# История изменений VK Web Lite

Последние версии — сверху. До 4.0 версии описаны по рабочим номерам (3.14–3.94).

## 5.00.18

- Тестовая сборка 226. «Фото в записях - страницей VK»: страницы фото, сохранённые прежними версиями, всё ещё содержали ключ `access_key` и открывались с «Ошибкой доступа» (отчёт 22.11, 5.00.17). Теперь ключ убирается у фото сообществ и при чтении сохранённого.

## 5.00.17

- Тестовая сборка 225. Исправлена настройка «Фото в записях - страницей VK»: страница фото сообщества открывалась с «Ошибкой доступа» (отчёт 22.11). Для фото сообществ ссылка теперь без ключа `access_key`; для фото людей ключ остаётся.

## 5.00.16

- Тестовая сборка 224. Исправлено обновление стены сообщества (отчёт 22.11, 5.00.15): каждое обновление кончалось ошибкой «сетевое обновление не выполнено», после чего данные страницы больше не считались свежими.
- Запрос `owners.getMainTab` при обновлении больше не передаёт пустой `start_from`: сама страница так не делает, а ответ на такой запрос был около 1 КБ вместо обычных сотен.
- Если сетевое обновление не удалось, а VK не отказал в доступе, экран обновляется прежним способом: страница присылает свои данные заново.
- В журнале появились причина и ответ VK при неудачном обновлении.

## 5.00.15

## 5.00.04

- Вспомогательные методы MediaStore Downloads помечены `@RequiresApi(29)`; их вызовы остаются в защищённых ветках Android 10+. Общий запрос удаления использует базовый столбец MediaColumns вместо Downloads.
- Уточнены комментарии о незавершённых загрузках и суффиксе имени файла. Добавлена инструкция восстановления Gradle-модели при ошибочном `current min is 1`; минимальный Android остаётся API 26.
- Подробности проверки — в docs/API_CHECK_5_00_04_RU.md.

## 5.00.03

- Неоднозначные отправки помечаются «Проверьте вручную»; меню предлагает проверить переписку, предупреждает о возможном дубле перед повтором и уточняет «Убрать из очереди».
- У голосовых есть постоянные локальные карточки с длительностью и состоянием, в том числе после перезапуска. Карточка заменяется настоящим сообщением только по точному номеру загруженного документа в той же переписке.
- У файлов видны подготовка, передача, загрузка и проверка; до отправки есть отмена с сохранением выбранных файлов и текста. Ограничения объясняются до выбора и в полосе файлов.
- Области нажатия реакций и выбранных файлов увеличены до 48dp; веб-режим сообщений обозначен постоянной полосой с входом или возвратом к лёгкому экрану.
- Прогресс сохранения музыки, остановка очереди и итог с несохранёнными треками доступны внутри раздела. Новые установки показывают короткие подписи навигации; сохранённый выбор компактного режима учитывается.
- Подробности, проверки и ограничения — в docs/UI_CHANGES_5_00_03_RU.md.

## 5.00.02

- После отмены уже прикреплённых файлов страница пересоздаёт композер. До очистки текстовая очередь не может отправить оставшиеся вложения.
- Ответ доставки передаёт номер сообщения в беседе. Один серверный номер не подтверждает повторно следующее сообщение; неоднозначные одинаковые ожидания остаются для ручного решения.
- Таймаут/остановка фоновой работы до передачи команды странице возвращает сообщение в очередь. Для уже начатой отправки сохраняется защита от автоматического дубля.
- У голосовых есть общий таймаут, отмена запросов и запасной таймер Android. Неопределённая доставка после начала messages.send показывается отдельно; поздний ответ старой операции игнорируется.
- Добавлены регрессии повторного ревью. Подробности — в docs/FIXES_5_00_02_RU.md.

## 5.00.01

- Отмена вложений передаётся странице; отложенные действия проверяют исходную переписку и номер операции. Завершение записи голосового после смены экрана не отправляет запись новому собеседнику.
- Очередь подтверждается после записи на диск; отправка ждёт сохранения состояния. Ошибка сохранения оставляет текст в поле ввода. Замена файлов атомарная, сравнение содержимого использует SHA-256.
- Скрытые WebView обрабатывают потерю renderer: экран сообщений пересоздаётся, фоновая работа завершается, окно кэша восстанавливается для следующей порции.
- Очистка картинок отменяет публикацию старых загрузок. Истории разных переписок не затираются в одной пачке; доставка пачек не откладывается бесконечно.
- Лимиты файлов проверяются по фактическому объёму; поле без multiple не отбрасывает лишние файлы молча. История страницы ограничена по памяти, чтение поколения музыкального кэша не ждёт файловый lock.
- Повтор отправки выбирается по ближайшей готовой переписке. Добавлены регрессионные проверки; подробности и ограничения проверки — в docs/FIXES_RU.md.

## 5.00.00

- **Кэш музыки в `Download/VkWebLite/Music`** на Android 10+: файлы записываются через MediaStore и остаются видны файловым менеджерам. «Открыть папку с музыкой» ведёт в стандартный раздел загрузок. Старые MP3 переносятся с проверкой копии; на Android 8–9 остаётся папка приложения.

## 4.99.9

- **Текущая песня выделена в списке музыки:** подсветка сохраняется на паузе, значок воспроизведения показывается только пока трек играет. Цвет подсветки следует выбранной теме.

## 4.99.8

- **Папка кэша в `Android/media/<пакет>/VkWebLite`:** музыка и картинки доступны через файловые менеджеры. При обновлении файлы из прежней `Android/data/<пакет>/files/VkWebLite` переносятся с проверкой содержимого; старый файл удаляется только после успешной копии. Очистка удаляет также остатки старого кэша, чтобы они не вернулись при следующем запуске.

## 4.99.7

- **Кэш — в своей странице.** Потоки треков без адреса («Кэшировать трек», «Кэшировать весь список/плейлист», автокэш
  «Моей музыки») ищет отдельное невидимое окно (`MusicCacheWorker`): оно открывает свою страницу музыки VK («Мои треки»
  или нужный плейлист), по очереди «открывает» треки в своём плеере, берёт адрес плейлиста HLS, ставит трек на паузу и
  отдаёт адрес кэшу. Страница человека, его плеер и музыка не трогаются (раньше 4.99.5 переключал плеер страницы).
  - Звук окна выключен всегда: каждый медиа-элемент глушится до начала воспроизведения (режим `cacheWorker` в 50_music.js).
  - Очередь управляемая: порциями по 20 треков одной страницы; «Остановить кэширование» (меню, уведомление) снимает и её;
    молчание дольше 45 с — порция «не удалась», страница открывается заново; без работы 60 с окно закрывается.
  - Окно живёт на общих таймерах WebView: пока оно открыто, приложение их не усыпляет (`AppVisibility.cacheRunning`).
  - Уведомление кэширования считает и треки, которые ещё ждут потока.
- Найденное поиском без адреса потока в кэш не попадает (страницы поиска у окна кэша нет); обычно адрес у него есть.

## 4.99.6

По отчёту 22.10 23:33 (4.99.3):
- **Адрес плейлиста HLS не запоминался ни разу:** плеер страницы запрашивает плейлист (`cs*.vkuseraudio.ru/s/v1/ac/…`)
  раньше, чем страница отмечает новый трек, а 4.99.2 брал трек в момент запроса. Поэтому не кэшировалось играющее, а
  «Кэшировать трек» ждал 18 с и отвечал «недоступно». Теперь загрузка плейлиста (основной и вариант из той же папки
  адреса — одна загрузка) достаётся треку, который играет через 1,5 с после неё и остаётся тем же ещё 1,5 с; если за
  это время началась другая загрузка (трек переключили) — адрес отбрасывается.
- **Нажатие на трек, который играет на странице, — пауза/продолжить.** Раньше уходила команда «включить»: VK ставил
  паузу, а проверка включения тут же нажимала «играть» — трек нельзя было остановить нажатием.

## 4.99.5

- **«Кэшировать весь список/плейлист» — и для треков без адреса:** если поток не раскрылся из списка и не пришёл от API,
  трек «открывается» в плеере страницы без звука — плеер грузит плейлист HLS, адрес уходит в кэш, — и так по очереди;
  в конце плеер возвращается к тому, что играло (трек, место, пауза, громкость). VK считает такие треки
  прослушанными. Автокэш «Моей музыки» плеер страницы не трогает. «Остановить кэширование» останавливает и очередь
  плеера; молчит дольше 45 с — оставшиеся считаются «не удалось».
- **APK меньше:** отдельный APK на архитектуру (`app-arm64-v8a-*.apk` — для телефона; `app-x86_64-*` — эмулятор;
  `app-universal-*` — общий), библиотеки FFmpegKit в APK сжаты. Почти весь размер (~50 МБ) давали они: ~20 МБ на
  архитектуру, две архитектуры, без сжатия.

## 4.99.4

- **«Моя музыка» — вся в кэш** (при включённом «Кэшировать музыку»): каждый трек списка, которого ещё нет в кэше, ставится
  в очередь по мере того, как страница отдаёт список, а трек, только что добавленный к себе, — сразу. Тихо: ход — в
  уведомлении кэширования, итог — в журнале («Моя музыка» в кэш: итог). Неудачный трек повторяется в следующий запуск.
- **Адрес трека без включения плеера:** в списке трека VK отдаёт адрес замаскированным
  (`audio_api_unavailable.mp3?extra=…#…`); теперь он раскрывается тем же алгоритмом, что у плеера страницы
  (`unmaskAudioUrl` в 50_music.js, с номером человека из данных трека). Раскрытое принимается, только если это https на
  серверах звука VK — если VK сменит алгоритм, кэш вернётся к прежним путям (плейлист HLS при воспроизведении,
  `audio.getById`). Этим же путём работают «Кэшировать весь список/плейлист».

## 4.99.3

- **Кэшируется всё, что играет:** порог «~30 с прослушивания» (4.95) убран — трек уходит в кэш, как только заиграл и
  известен адрес его потока (на странице VK — когда плеер загрузил плейлист HLS). Пауза и перемотка того же трека
  повторно его не ставят. `ListenTracker` и его тест удалены.

## 4.99.2

- **Кэш музыки, играющей на странице.** По отчёту и дампу 22.10: мобильная VK отдаёт адрес трека только зашифрованным
  (`audio_api_unavailable.mp3?extra=…` в списке трека), в ответах API потоков нет, а играет страница HLS через MSE — у
  медиа-элемента адрес `blob:`. Кэшу (4.95–4.99.1) брать адрес было неоткуда, и прослушанные треки не сохранялись.
  Теперь адрес плейлиста HLS берётся из запроса самого плеера страницы (`NetTap.onRequest`, новое): он запоминается за
  треком, который играл и в момент запроса, и когда плейлист пришёл (иначе — не запоминается). «Кэшировать трек» для
  трека без адреса получает его тем же путём.
- `NetTap`: плейлисты (`mpegurl`) считаются текстовыми ответами.

## 4.99.1

- **Исправлено падение при «Поделиться»** (журнал, отчёт о сбое, собранное для разработки): поставщик папки приложения
  (4.99) получил тот же адрес, что FileProvider, — `${applicationId}.files`. Android отдавал адрес первому из них, у
  которого нет путей FileProvider, и каждое «Поделиться» завершало приложение (в том числе кнопка на экране сбоя).
  Адрес поставщика папки теперь `${applicationId}.documents`.
- Тест `ManifestProvidersTest`: адреса поставщиков в манифесте не повторяются, у FileProvider есть пути.

## 4.99

- **Кэш музыки — в папке приложения, а не в «Музыке».** Треки лежат в `Android/data/<пакет>/files/VkWebLite/Music`
  («Исполнитель - Название (номер).mp3»); файлы 4.90–4.96 из корня папки и 4.97–4.98 из «Музыка/VkWebLite» переносятся
  сюда при запуске. Папка удаляется вместе с приложением. Разрешения на музыку и системные запросы удаления (4.98)
  больше не нужны и убраны; запись в общую память (Android 8–9) осталась только для переноса.
- **Папку открывает само приложение:** Настройки → Сохранённые данные → «Открыть папку приложения» и «Открыть папку с
  музыкой» в меню трека. Android 11+ не показывает `Android/data` файловым менеджерам, поэтому папка видна в системном
  приложении «Файлы» через свой поставщик документов (`files/AppFilesProvider`): просмотр, открытие, копирование,
  удаление. Удалённый там трек сразу пропадает из кэша; при возврате в приложение папка перечитывается.
- **Остальные кэши — туда же, где есть общая память:** картинки (`VkWebLite/Images`, прежний кэш во внутренней памяти
  удаляется) и собранное для разработки (`VkWebLite/Dev`, переносится). Сохранённая переписка, журнал событий и данные
  входа остаются во внутренней памяти: на Android 8–10 `Android/data` могут читать другие приложения с доступом к файлам.
- Тест: `AppFilesProviderTest` — документы поставщика не выходят за пределы папки (`..`, ссылки; ссылки раскрываются
  через `toRealPath`, а не `canonicalFile`, который на Windows их не раскрывает).

## 4.98

- **Кэширование списка — и в фоне.** Пока очередь кэша не пуста, работает сервис (`MusicCacheService`, тип dataSync):
  держит процесс, процессор и Wi‑Fi, в шторке — «Кэширование музыки: осталось N, сохранено M» с кнопкой «Остановить».
  Раньше Android мог остановить свёрнутое приложение посреди «Кэшировать весь плейлист». Прослушанные треки сервис не
  запускают. «Остановить» из уведомления снимает и части списка, для которых страница ещё ищет потоки.
- **После переустановки** (Android 10+) приложение один раз просит разрешение на чтение музыки: с ним прежние файлы
  «Музыка/VkWebLite» снова считаются кэшем и не качаются заново. Удалить такой файл («Удалить из кэша», «Аудиофайлы» в
  «Сохранённых данных») Android 11+ даёт только с согласия человека — показывается системный запрос.
- Имя файла с дописанным MediaStore « (1)» тоже узнаётся как трек кэша.
- Подстановка файлов кэша в очередь вынесена из `ChatMusic` в `InAppQueue.withCached` и покрыта тестом.

## 4.97

- **Кэш музыки — сразу в хранилище телефона.** Закэшированный трек — mp3 с тегами в «Музыка/VkWebLite»: его видят другие
  плееры и файловый менеджер, а приложение играет его оттуда же (Android 10+ — через MediaStore, без разрешений;
  Android 8–9 — с разрешением на запись, без него — в папке приложения до выдачи разрешения). Файлы 4.90–4.96 из
  `Android/data/…/VkWebLite` переносятся в «Музыку» при запуске. Имя файла — «Исполнитель - Название (номер).mp3».
- **Кэшировать по нажатию:** в меню трека «Кэшировать трек» (вместо «Скачать трек» — это теперь одно и то же) и
  «Удалить из кэша»; работает и при выключенной настройке «Кэшировать музыку».
- **Массовое кэширование:** «Кэшировать весь список» (Мои треки, найденное) и «Кэшировать весь плейлист» — все
  показанные треки, которых ещё нет в хранилище. Потоки страница получает порциями по 50 запросом `audio.getById`, без
  включения плеера; итог — «в хранилище N из M, не удалось K». «Остановить кэширование» снимает с очереди всё
  неначатое (`CacheBatch`, `MusicStreams`).
- **Значок «в хранилище»** у трека в списке; обновляется, как только трек сохранён или удалён.
- «Аудиофайлы» в «Сохранённых данных» удаляют файлы кэша из «Музыка/VkWebLite».

## 4.95

- **Музыка всегда сохраняется в MP3, дальше — из кэша.** Настройки «Конвертировать музыку в MP3» больше нет: mp3 остаётся

  записи «Музыки», оставшиеся «в ожидании» после убитого процесса.

  глушится, при восстановлении прежнего не слышно его начала. Пока страница ищет поток, показывается «Ищу аудиопоток…».
- **Исправлено (код ревью 4.94):**

  - «Показать ещё» искался по подстроке во всём тексте ссылки и мог нажать чужое;
  - обложки в списке снова ~300 px (большая — только в теги файла);
  - сегменты HLS без расширения назывались `.bin`, и FFmpeg мог их не открыть: теперь имя — по содержимому;
  - Android 8–9: скачанный файл сканируется (виден плеерам сразу), после выдачи разрешения скачивание продолжается само;
  - «Музыка» в «Сохранённых данных» снова удаляет только списки; аудиофайлы — отдельный пункт «Аудиофайлы».

  играет — поток трека (адрес с путём `/expires/…`), а превью роликов раздела, на котором страница сейчас, — нет.
- **Экран гас во время видео и клипов.** Ни один проигрыватель не просил систему держать экран включённым, и через
  время из настроек Android («Время до отключения экрана») он гас посреди ролика. Теперь (`ui/ScreenAwake.kt`):
  - свой проигрыватель видео и клипов — экран держится, пока ролик играет или подгружается для игры; на паузе, после
    конца ролика и при ошибке гаснет как обычно;
  - встроенный проигрыватель VK (ролики без файла, трансляции) — раз в 5 с спрашивает страницу, играет ли ролик;
    ролика на странице не видно — экран держится, пока окно открыто;
  - видео страницы во весь экран в главном окне — экран держится, пока оно во весь экран.
- **Поиск музыки показывал пустой список (отчёт и дамп 4.86).** Главная причина: страница поиска m.vk получает
  найденное ответом API `catalog.getAudioSearch` (объекты `{id, owner_id, artist, title, duration, url}`), а скрипт
  читал только вёрстку с `data-audio`. Ввод запроса в поле страницы давал «найдено 0», хотя VK вернул 21 трек; на
  странице поиска, открытой переходом, в вёрстке лежали подборки страницы, и из 24 чужих треков исполнителю
  подходил 1. Теперь:
  - список страницы поиска — из ответа API для её запроса (и продолжений `catalog.getSection` / `getBlockItems`);
    кортежи вёрстки этой страницы в него не подмешиваются; ответ, пришедший раньше смены адреса на поиск, начинает
    список нового адреса; заготовка экрана поиска без запроса и ответ другого запроса не считаются результатами;
  - список приходит целиком (`complete`), без бесконечных попыток догрузки;
  - у найденного есть адрес звука, а нажать на него на странице нельзя (вёрстки с `data-audio` у результатов нет):
    его играет приложение своим проигрывателем, очередь — найденные треки по порядку. Мини-плеер экрана музыки
    показывает этот трек, его кнопки и перемотка управляют им; когда своя музыка кончилась или заиграла страница —
    снова музыка страницы. Адрес принимается только с серверов звука VK (`SafeUrls.audio`).
- **Отбор «Только …» в поиске по исполнителю** отбрасывал найденное, если имя у треков записано иначе:
  - в результатах поиска VK может выделять совпавшие слова разметкой (`<em>…</em>`): исполнитель «Король и Шут» с ней
    переставал совпадать с собственным именем. Разметка теперь убирается при чтении трека (`plainText` в

  - если отбор ничего не оставил из окончательного списка (весь список или ожидание вышло), а VK что-то нашёл, —
    показывается всё найденное, переключатель «Только …» выключается, и об этом короткое сообщение (раз за поиск:
    включили снова — так и остаётся);
  - поиск исполнителя из переписки: ожидание результатов теперь отсчитывается с отправки команды странице, а не с
    нажатия. Пока на медленной сети открывался раздел музыки, семь секунд ожидания проходили впустую, и экран успевал
    сказать «ничего не найдено» до начала поиска.

## 4.62

Свой интерфейс сообщений — по разбору таймеров экрана и окна чтения:

### 3.18: страница под своим экраном не рисуется
Пока открыт свой экран (музыка, друзья и сообщества, страница человека), WebView скрыт (`INVISIBLE`, `MainActivity.syncWebViewVisibility`).
Размер окна сохраняется — вёрстка страницы считается как обычно, поэтому данные, прокрутка и догрузка работают; но Chromium
её не рисует: анимации, GIF и превью видео VK под непрозрачным экраном больше не тратят процессор и графику. Окно чтения
сообщений и фоновая проверка были скрыты и раньше.

Чего в скрытой странице Chromium не делает, эмулирует `assets/page_visibility.js` (ставится первым, до скриптов VK), и только
пока окно действительно скрыто:
- **кадры** (`requestAnimationFrame`) — таймером с запросом 100 мс; Chromium в скрытой странице может выровнять его до секунды
  (если звук не играет), так что дорисовка списков по кадрам бывает медленнее обычной, но не встаёт, а циклы анимаций не крутят процессор;
- **пересечения** (`IntersectionObserver`, на нём держится бесконечная лента): свой расчёт по положению элементов
  (`getBoundingClientRect`, с `rootMargin` и порогами) — при `observe` и после прокрутки приложением;
- **прокрутка**: приложение прокручивает страницу для догрузки (`PageList.scrollToEnd`, музыка, старые сообщения) и вызывает
  `__vkWebVisibility.afterScroll(цель)` — событие `scroll` и сверка пересечений; после прокрутки «до конца» видимая метка конца
  ленты сообщается заново, чтобы лента догрузилась, даже если метка была видна и раньше;
- **без задержки таймеров**: данные своих экранов и окна чтения уходят приложению следующей задачей (`MessageChannel`), а не
  таймером, который в скрытом окне срабатывал бы через секунду; несколько ответов одной пачки всё равно собираются в одно сообщение.

Страница о скрытии по-прежнему не узнаёт (`document.hidden = false`), музыка в скрытом окне играет дальше. Кнопка «Страница VK»
показывает окно — оно сразу снова рисуется, и работают настоящие кадры и наблюдатели.

### 3.25: список музыки «сжимался» после открытия
**Что было.** При открытии показывались сохранённые «Мои треки» целиком, затем приходила первая порция от страницы — и список
сокращался до неё. Слияние вправе выбросить сохранённое, только если страница прислала список целиком; для музыки это

### 3.26: дубли и «скачущий» кэш переписки (по отчёту 3.24)

### 3.29: кэш переписки «дышал» при каждом входе (по отчёту 3.26, 08:10)
**Что показал отчёт.** Второй вход в ту же переписку: показано 35 сохранённых, затем «1 сообщение» → «сохранено 16380 байт», затем
«32 сообщения» → снова «сохранено 16380 байт». Размер тот же, но запись не пропущена как «не изменилось» — значит, между двумя
порциями содержимое различалось, и на диск каждый раз уходила то одна версия, то другая.

**Причина.** Последнее сообщение страница сначала присылает из списка диалогов — в урезанном виде (без имени автора, часто без
вложений), а полную версию — позже, ответом по истории. `HistoryMerge.messages` заменял сообщение с тем же id целиком, поэтому
при каждом входе последнее сообщение сначала «беднело», потом снова «обогащалось» — это и было заметно как «опять что-то
подгружается» — и каждый раз перезаписывалось на диск.

**Исправлено.**
- `HistoryMerge.richer`: то же сообщение из новой порции главнее, но не беднее — пустые поля (автор, время, фото) не затирают
  известные; если у новой версии нет фото, а у известной есть, остаётся известная целиком (в тексте урезанной бывает подпись
  «[Фото]» вместо картинки). Текст исправленного сообщения берётся из новой порции.
- `OfflineStore.write`: первая запись файла после запуска сверяется с тем, что уже лежит на диске, а не пишется заново
  (раньше «что записано» хранилось только в памяти, и каждый вход перезаписывал переписку).
- Диагностика: если у тех же сообщений всё же меняются поля, в журнале «переписка: изменились поля что=c123: автор+фото 0→1» —
  по отчёту будет видно, какое поле «дышит», если что-то осталось.
- Тесты: урезанная версия не затирает полную; повторный вход (сохранённое → неполная порция → полная) оставляет сохранённое
  без изменений; подпись «[Фото]» не добавляется.

3.29 исходило из предположения, что «урезанная» версия последнего сообщения отличается **пустыми** полями. Перепроверка

### 3.31: музыка и плейлисты
Экран музыки разделён: сверху переключатель **«Музыка / Плейлисты»**.
- **Музыка** — «Мои треки», как раньше.
- **Плейлисты** — список плейлистов (обложка, название, число треков, автор, если страница его показала). Нажатие открывает треки
  плейлиста; кнопка «К плейлистам» или системная «Назад» возвращает к списку. Трек играет сама страница, мини-плеер и плеер с
  перемоткой общие для обоих разделов. Переключение разделов и открытие плейлиста делает сама страница силами VK (как нажатие
  ссылки), поэтому **музыка при этом не прерывается**.
- Список плейлистов сохраняется для работы без сети (`playlists.json`, удаляется вместе с музыкой в настройках). Треки плейлистов
  не сохраняются — звук всё равно идёт из сети.

**Как устроено.** Страница музыки одна, а списков в приложении два — «Мои треки» и треки открытого плейлиста. Страница сообщает
приложению, что на ней сейчас (`page`: `my` / `playlist` / `other` и свой адрес), а `MusicRouting` решает, в какой список идут
треки: страница, перешедшая на другой плейлист, не подмешивает его треки в открытый, а рекомендации и поиск не попадают никуда
(тесты `PlaylistsTest`). Плейлисты ищет `assets/vk_lite/55_playlists.js` двумя способами — в JSON-ответах страницы (формы API и
веб-версии) и в вёрстке (ссылки на плейлист: `…audio_playlist<владелец>_<номер>`, `…/playlist/…`); если плейлистов на странице нет,
скрипт сам находит ссылку на страницу плейлистов («Плейлисты», «Показать все» рядом с заголовком) и переходит по ней.
Треки, видео, фото и записи за плейлисты не принимаются (JS-проверки).

**Важное допущение.** Как именно мобильный VK размечает плейлисты, надёжно не известно (проверить сайт при разработке было
нельзя), поэтому распознавание — по нескольким признакам. Если плейлисты не нашлись, экран говорит об этом, а в журнал (метка
SCRIPT, уровень WARN) пишется «плейлисты не найдены. стр=…; ссылки: …» — страница и самые показательные ссылки без номеров и
ключей: по ним видно, как искать плейлисты на самом деле.

Также: догрузка плейлиста использует явный ответ сервера «есть ли ещё»; включение трека «Моих» со страницы плейлиста возвращает
страницу на главную и включает его там (запрос действует 60 секунд); кнопка «Назад» внутри экрана закрывает плейлист, а не весь
раздел музыки.

### 3.38: отправленное сообщение висело как «отправляется» (по отчёту 3.36, 15:34)
**Что показал отчёт.** 15:34:16.100 отправка из очереди; 16.248 страница нажала «Отправить»; 16.432 прошёл `messages.send`; 16.4–16.9

**Причина.** Доставленным сообщение из очереди считается, только когда в истории есть настоящее своё сообщение с номером (`c…`,
`OutboxLogic.reconcile`) — «нажато» не значит «принято». Окно чтения такого сообщения не получало: ответ `messages.send` оно не
разбирало, а новые сообщения приходят по долгому опросу VK (`queuev4`/`ruim`), который не метод API и в перехват не попадал.
В истории появлялось только черновое «+1» без номера. Приходилось ждать 12 секунд и перезагружать страницу.

**Исправлено.** Успешный ответ `messages.send` — уже доказательство доставки (сервер принял сообщение). Окно чтения
(`vk_reader.js`, `onSendResponse`) перехватывает его и: (1) шлёт приложению `delivered` (переписка, текст; счётчик `n`, чтобы два
одинаковых «ок» подряд не отбросились как повтор); приложение снимает из очереди первое ожидающее сообщение с этим текстом
(`OutboxLogic.deliveredByServer`, `ChatOutboxDriver.onDelivered`) и отправляет следующее; (2) если в ответе есть номер
сообщения в беседе, добавляет настоящее сообщение в историю окна — оно сразу приходит с номером. Ошибка в ответе — не доставка.
Прежний путь (опрос истории, перезагрузка через 12 секунд, «не подтверждено» через 45) остаётся запасным.

Фоновая проверка (`HeadlessSync`) сигнал `delivered` использует с 3.43.

### 3.51: ответы на сообщения, старые сообщения без предела, голосовое без прокрутки, друзья
- **Ответы.** Сообщение-ответ показывает над текстом цитату (автор и начало того, на что ответили); нажатие на неё ведёт
  к тому сообщению (прокрутка и подсветка), а если его ещё нет в списке — старые догружаются, пока оно не найдётся (до 20
  порций) или пока не дойдём до начала переписки. Так же работает ответ на ваше сообщение. Долгое нажатие на сообщение →
  «Ответить»: над полем ввода полоса «Ответ · Автор» (нажатие — к сообщению, ✕ — отменить). Ответ уходит запросом
  `messages.send` с `forward {is_reply}` от имени страницы мессенджера (в композере страницы так не ответить); без сети —
  подсказка, текст остаётся в поле. Страница: `messageReply`, `sendReply` в `vk_reader.js`; приложение: `ChatReply`,
  `HistoryMerge.mergedReply`, сохранение в `OfflineStore`.
- **Старые сообщения без предела.** Раньше они догружались только прокруткой скрытой страницы, и мессенджер VK через
  несколько страниц переставал отвечать — выше определённого места переписка не листалась. Теперь — запросом
  `messages.getHistory` (по 100, смещение — сколько уже есть); пустой ответ — «переписка с самого начала», дальше не просим.
  Держится до 2000 сообщений (было 1000). Без данных входа — прежний путь.
- **Вызов API от имени страницы** перенесён в общий перехват (`shared/net_tap.js`, `NetTap.api`): им пользуются и главное
  окно (лайки, друзья), и окно чтения (старые сообщения, ответы).
- **Голосовое листало переписку.** Время под полосой (ширина «по содержимому») меняется каждые полсекунды, и каждая смена
  пересчитывала раскладку всего списка. Теперь ширина постоянная.
- **Проверка экранов по собранным данным страниц** (прогон ответов VK из дампа через скрипты): страницы сообществ и людей,
  «Мои подписки» и плейлисты собираются верно. **Друзья** — нет: m.vk.ru отдаёт список друзей в вёрстке и не вызывает
  `friends.get`, своему экрану было не из чего строить список. Теперь, если страница его не запросила, список (и заявки)
  запрашиваются от её имени; продолжение — так же.

### 3.54: меню по нажатию, «Переслать», видео в переписке, звонки
- **Действия с сообщением — по обычному нажатию** на пузырь (раньше — зажать и подождать; долгое нажатие тоже работает).
  Нажатие на ссылку в тексте открывает ссылку, на вложение — вложение; мимо них — меню. Выделение текста убрано: оно
  перехватывало нажатие, а для копирования есть «Копировать текст». Ссылки текста продублированы пунктами меню
  («Открыть: …») — так они доступны и с экранным чтецом. Неотправленные по нажатию, как и раньше, — «повторить / удалить».
- **«Переслать» в другую переписку VK** (кроме «Поделиться» в другие приложения): список переписок, первой всегда своя —
  «Избранное (себе)», даже если её нет среди загруженных. Пересылка — запрос `messages.send` с `forward` от имени страницы,
  как ответ; итог — подсказка «Переслано: …» или причина. Пункт «Переслать файл» у файла переименован в «Поделиться
  файлом», чтобы не путать.
- **Видео и клипы играют прямо из переписки**, без перехода в главное окно: страница отдаёт файлы ролика (`video.get` с
  ключом доступа, запасной способ — `video.getByIds`, как у сайта видео), и открывается проигрыватель приложения — mp4 до
  720p (трансляция — поток HLS), клип играет по кругу. Файл не играет — встраиваемый проигрыватель VK; нет и его или
  страница не ответила за 8 с — страница видео, как раньше. Кнопка сверху открывает страницу видео (комментарии, лайки).
  Видеосообщения («кружки») играют там же. Адреса — только https на серверах VK (`AppConfig.isImageHost`).
- **Звонки — с подробностями** вместо «[Звонок]»: карточка «Исходящий/Входящий/Пропущенный (видео)звонок» и итог —
  длительность, «Отменён», «Вы не ответили», «Собеседник отклонил»; групповой звонок — кто начал, сколько участников и
  ссылка «присоединиться» (только на VK). Строка в списке диалогов тоже говорит, что было: звонок, видео, клип, музыка,
  файл, голосовое (раньше любое сообщение без текста было «[Фото]»).
- Тесты: Kotlin — своя переписка первой при пересылке, разбор итога пересылки и файлов видео (чужие адреса отбрасываются),
  карточки звонков; JS — запросы пересылки и файлов видео, карточки звонков и групповых звонков, строка диалога.

Проверить на телефоне (по отчёту): отдаёт ли `video.get` на m.vk.ru файлы у видео из сообщений (иначе сработает
встроенный проигрыватель или страница — в журнале «файлы видео получены / нет»), и приходит ли у звонков `initiator_id`.

### 3.55: разбор дампа — музыка из переписки играет само приложение
- **Что показал дамп (9 октября, 3.53):** трек из сообщения не нашёлся в вёрстке переписки, приложение перешло в раздел
  музыки, и страница искала его запросом `catalog.getAudioSearch` — трижды подряд («SISENIN — Блуд»). Поиск трек нашёл
  (первым же результатом), но результаты страница рисует новой вёрсткой без `.audio_item[data-audio]`, поэтому нажать
  его было не на чем. Главное — в ответе API у трека есть **`url`: поток HLS на `vkuseraudio.ru`**.
- **Теперь трек из сообщения играет само приложение**, прямо в переписке, без нажатий по вёрстке и без перехода: окно
  чтения достаёт адрес потока — из ответа с самим сообщением (если он там есть и свежий), `audio.getById` по номеру и
  ключу доступа, иначе поиском по «Исполнитель — Название» (`catalog.getAudioSearch`, как сама страница; точное
  совпадение важнее «Блуд (mp3bob.ru)»). Заглушка `audio_api_unavailable` не принимается. Играет тот же проигрыватель, что
  и голосовые (`VoicePlayer`, вид звука «музыка», постоянный звуковой фокус) — поэтому голосовое и трек больше не звучат
  одновременно (риск из 3.52). Полоса над полем ввода: «Загрузка…», пауза, время, остановить.
- Запасные пути остались: нет адреса или поток не проигрался — вложение нажимает страница (как в 3.53), не вышло и так
  или страница молчит 10 с — раздел музыки.
- Адреса звука — только https на `vkuseraudio.ru/.net/.com` и доменах VK (`AppConfig.isAudioHost`).
- Остальное в дампе в порядке: группы, сообщества, запись с лайками, друзья.

### 3.56: видео и клипы — во весь экран с сохранением пропорций
- Проигрыватель видео из переписки растягивает кадр по размеру экрана, сохраняя соотношение сторон, — до тех пор, пока
  одна из сторон не упрётся в край экрана (горизонтальное видео — по ширине, вертикальный клип — по высоте), и ставит его
  по центру. Раньше видео показывалось в собственном размере: ролик 480p на телефоне занимал часть экрана. При повороте
  экрана кадр вписывается заново. Встроенный проигрыватель VK (запасной путь) и так занимает весь экран.

### 3.57: перемотка клипов в ленте «Клипы»
- Полоса перемотки внизу экрана (потянуть или нажать в нужное место — время показывается над пальцем) была только на
  странице одного клипа (`/clip-1_2`). Теперь она есть и в разделе «Клипы» — в ленте (`/clips…`) и в клипах автора.
- В ленте на странице сразу несколько роликов (следующий готовится заранее), поэтому полоса управляет тем, который идёт и
  больше всех виден на экране; соседние не трогаются. Жесты по полосе не листают ленту и не ставят клип на паузу.
- Клип из переписки (свой проигрыватель приложения) перематывается полосой проигрывателя: нажатие на видео показывает
  её вместе с кнопками назад/вперёд.

### 3.58: прочитанное сбрасывает счётчики, сообщение с файлами видно сразу
- **Переписка отмечается прочитанной.** Окно чтения скрыто, и VK не считал переписку открытой: счётчик непрочитанных на
  сайте и в приложениях VK не сбрасывался. Теперь, когда переписка на экране и в ней новое входящее (и при возврате на
  экран), страница отправляет `messages.markAsRead` (вся переписка). В фоновой проверке сообщений — нет: там ничего не
  читают. Ошибка — в журнал.
- **Записи сообществ.** По дампу: счётчик «новых записей» у сообщества (`catalog.getGroups` → `counter`, например 7) не
  уменьшался после открытия сообщества — страница отправляет «открыта группа», но записи на её собственном экране не
  показывались (её закрывает свой экран). Теперь записи, которые побывали на своём экране, по очереди (раз в 1,2 с)
  выводятся и на экран страницы — VK отмечает их своим же наблюдением, как при обычном просмотре. Каким запросом VK
  считает просмотр, в дампах нет: в журнал пишется название такого запроса («отметка просмотра — запрос …»), если он
  уйдёт, — по отчёту станет видно, сработало ли.
- **Сообщение с файлами — сразу пузырём «отправляется»** (текст и 📎 названия файлов) с момента нажатия; когда настоящее
  сообщение пришло — пузырь убирается, и оно показывается как обычно. Не отправилось — пузырь убирается (файлы остаются
  в полосе). Причина задержки: после отправки с файлами окно чтения ждало следующего чтения истории, а мессенджер получает
  новое долгим опросом, не методом API, — сообщение появлялось только после перезахода. Теперь оно запрашивается сразу
  (`messages.getByConversationMessageId` по номеру из ответа отправки, без номера — последние сообщения; два повтора при
  ошибке). Признак «с файлами» — и по самому запросу отправки (`attachment`). Номер из ответа веб-клиента (`cmid`) теперь
  понимается и для обычного текста — отправленное попадает в историю сразу.

### 3.59: полный код ревью и разбор отчёта 3.58
Ревью шло по шести областям (сообщения, окно чтения, скрипты страниц, главное окно, данные и фоновая работа,
интерфейс); каждая находка перепроверена по коду. Исправлено:

**Сообщения**
- Автообновление и «прочитано» не работали при возврате на экран: проверка «экран виден» внутри onStart() всегда была
  ложной (жизненный цикл ещё CREATED). Теперь — свой признак видимости.
- Ответ пересылки или ответа на сообщение принимался окном чтения за обычную отправку: в историю вставал чужой текст
  (последний отправленный) под номером пересланного, «доставлено» могло снять с очереди другое сообщение. Теперь
  свои запросы отличаются (`forward`), а отправленное в эту же переписку запрашивается целиком.
- Полоса музыки, которую играет приложение, пряталась от событий страницы (в том числе от «остановлено» в ответ на нашу
  же остановку) — трек оставался без управления. Повторный сбой одного и того же адреса больше не вызывает запасной
  путь дважды.
- После ухода с экрана пришедший адрес трека или файлы видео больше не включают звук и не открывают окна поверх других
  приложений; закрытый экран больше не получает данных от страницы.
- Смена переписки сбрасывает выбранные файлы и незаконченную отправку (раньше файлы ушли бы не тому, а кнопки были
  отключены до 3 минут); полоса «Ответ» и файлы не остаются над списком диалогов.
- Пузырь «отправляется» больше не пропадает от догрузки старых сообщений (сравнение по номеру сообщения).
- Поздно пришедшее подтверждение не стирает новый текст в поле ввода.
- «Переслать» показывает все переписки и когда экран открыт ради одной (из друзей, из уведомления).
- Открытие переписки, когда показан сам сайт VK, — переход на странице, а не пустой «свой» экран со спиннером.
- Видео, поставленное на паузу, после возврата из фона продолжается с того же места и на паузе.
- Окно чтения: объекты страницы больше не изменяются (замороженные бросали исключение), закреплённое сообщение не
  сбивает счёт при догрузке старых, догрузка останавливается на пределе 2000, поиск трека и обложки по номеру — точный
  («1_2» больше не совпадает с «11_23»), свой запрос не «перезахватывает» данные входа.

**Главное окно и страницы**
- Страницы с серверов файлов VK (userapi.com и т. п.) и после форм за пределами VK открываются во внешнем браузере, а
  не во весь экран приложения (риск поддельной страницы входа). Скачивание файлов — как раньше.
- Раздел, раздел VK и настройки по запуску из чужого приложения больше не открываются; после пересоздания экрана
  просьба не повторяется. Ссылки из данных страниц — только разрешённых схем (file:// и т. п. роняли приложение).
- Падение WebView: прежнее состояние не восстанавливается (иначе та же страница роняла его снова по кругу).
- Выход из аккаунта: история переходов очищается после загрузки новой страницы («Назад» вела на страницу прежнего
  аккаунта); убираются уведомление, фоновые задания, отчёт о сбое и переданные файлы.
- Плеер в шторке ждёт следующий трек 30 с, а не 3: на Android 12+ медленный следующий трек останавливал плейлист.
- Обновление сессии по таймеру своего экрана — не в фоне.
- Переданные файлы: у каждой передачи своя папка, старые удаляются через час (раньше новая передача стирала файлы
  предыдущей, которые другое приложение ещё читало).
- Перемотка клипов прячется, пока открыто окно поверх клипа (комментарии, «Поделиться»), и не считает ничего в фоне.
- Увиденные записи: очередь останавливается, как только страницу VK стало видно или открыта другая (страница не прыгает
  перед глазами), записи ищутся точно по номеру, не найденные повторяются, когда страница их покажет; сообщаются только
  записи, пришедшие от страницы.
- Стена: больше 300 записей не просит («загрузка…» без конца); поздний ответ лайка не сбрасывает данные другой страницы.
- Музыка: поиск трека из переписки вводится только на странице музыки; разбор добавленных треков — один раз на пачку.

**Данные и фон**
- Неотправленное в фоне больше не «застревает»: после фоновой работы, если в очереди что-то осталось, задание
  ставится снова (не чаще раза в 30 с).
- Обработчик падений: стандартная обработка — в finally (иначе при нехватке памяти процесс оставался живым и
  зависшим); в отчёт о сбое — только свои строки журнала процесса, дамп зависания — не больше 30 тыс. знаков.
- Записи на диск — с fsync (очередь неотправленных не пустеет при пропаже питания); «время использования» сохранённого
  обновляется и без изменений — часто открываемое не удаляется первым.
- Удаление очереди из настроек: память сбрасывается до удаления файла (удалённое не возвращалось и не отправлялось).
- Журнал и отчёт: тексты ошибок JSON (в них — само сообщение) больше не пишутся. Сбор данных страниц маскирует текст
  отправляемых сообщений, поисковые запросы и длинные строки без имён.
- Сбор данных: предел — в байтах, чистка — через временный файл. Слежение за подвисаниями — одна цепочка кадров.

**Интерфейс**
- Время из данных страницы ограничено 2100 годом (огромное значение роняло список при каждом показе).
- Экранный чтец читает текст записи; у комментариев — подпись. Картинки больше цели уменьшаются до неё (просмотр фото
  выходил за бюджет памяти). Сохранённые записи получают новые поля фото (страница фото). Текст записи для «Поделиться» —
  без разметки VK. Просмотр фото после пересоздания открывается на том же фото.

**По отчёту 3.58**
- «Прочитано» работает (`messages.markAsRead` в журнале), видео из переписки играет своим проигрывателем, лайки ставятся.
- Трек из переписки: адрес по номеру проиграл, а адрес из ответа с сообщением — нет (код 1/-1); теперь при сбое сначала
  берётся свежий адрес по номеру, и только потом трек нажимает страница.
- Раздел «Музыка»: трек «Моих треков», нажатый сразу после открытия главной (треков в вёрстке ещё нет), больше не уходит
  в плеер страницы с ошибкой — включение ждёт, пока страница нарисует список.
- Увиденные записи не находились в вёрстке страницы (/id, /club): теперь в журнале — что именно в вёрстке есть (ссылки
  на записи, элементы записей, высота), по следующему отчёту станет ясно, как страница их рисует. Отметка просмотра
  больше не пишется на странице музыки. По дампу счётчик новых у одного сообщества за день стал 1 (было 30).

Найдено, но не менялось (нужны данные или риск поломки): вход через OK и Mail остаётся внутри приложения целиком
(все поддомены); загрузки файлов из любых фреймов без подтверждения; одновременная двойная загрузка одной картинки может
завысить счёт кэша; страница видео по таймауту своего экрана может открыться в фоне.

### 3.60: музыка в переписке — как в разделе «Музыка»; повторный разбор журнала и дампа
- **Музыка из сообщений получила возможности плеера раздела «Музыка»** (`media/ChatMusic.kt`, `media/ChatQueue.kt`):
  - очередь — все треки переписки по порядку (и в пересланных): «вперёд», «назад» (после 3 с — к началу трека),
    следующий включается сам, когда трек доиграл;
  - перемотка ползунком, обложка, название и исполнитель, время; нажатие на звучащий трек — пауза/продолжить;
  - уведомление с кнопками, экран блокировки, гарнитура (через тот же сервис плеера, что у раздела «Музыка»);
  - игра в фоне — по настройке «Фоновое воспроизведение» (как у раздела); отключили наушники — пауза;
  - музыка страницы и музыка переписки не звучат вместе: включили одну — другая замолкает;

    только запасной (по отчёту 3.58 он не проигрывался). Трек не проигрался — свежий адрес, не помогло — пропуск.
  - Запасной путь (трек нажимает сама страница) остался; у него — только пауза и время.
- **Повторный разбор отчёта 3.58** (журнал целиком, по всем предупреждениям):
  - Раздел «Музыка», плейлист: после смены плейлиста нажатие на трек ставило на паузу прежний трек, а новый не
    начинался (четыре нажатия подряд — «paused=true, позиция=7»). То же сразу после открытия полного списка «Моих
    треков» («медиа-элемента нет»). Теперь, если через 1,5 с звука нет, нажатие повторяется — кнопкой «играть» в строке
    трека. Нажатие на трек, который уже звучит (пауза по желанию), не повторяется.
  - Остальное по журналу: «прочитано» уходит, видео из переписки играет своим проигрывателем, лайки ставятся
    (в дампе — `likes.add` приложения с ответом сервера), друзья и сообщества обновляются; «нет скрипта приложения» на
    странице друзей — команда до загрузки страницы, следом данные пришли. Подвисания до 0,2 с — разбор длинной
    переписки и разметка, не ошибки.
  - Дамп: счётчик новых записей одного сообщества — 30 → 1 за день, другого — растёт (13), его не открывали.
    Как страница рисует записи, в дампе нет (только ответы API) — это покажет журнал 3.59+.

### 3.61: переписка и список диалогов больше не прыгают
- **Переписка.** При каждом обновлении (статус отправки, обновление по таймеру, обложка видео, новые данные страницы)
  экран «возвращал» прокрутку к строке, которая была вверху, когда обновление началось: прокрутка пальцем обрывалась, и
  переписка дёргалась назад. Теперь место восстанавливается, только если сверху правда добавились старые сообщения,
  список не листают и строка перед глазами действительно сдвинулась; остальное держит сам список.
- **Список диалогов.** Страница присылает диалоги частями (в журнале: 9, затем 22). Настоящий порядок ставился по первой,
  неполной части — 22 строки переставлялись, и потом ещё раз. Теперь порядок меняется один раз — по полной порции; до
  неё строки обновляются на своих местах.

### 3.62: переписка не пустеет при открытии
- Открытие переписки очищало список и заполняло его заново: сначала сохранённым с диска (чтение в фоне — список успевал
  мелькнуть пустым), потом данными страницы. Теперь последние 8 открытых в этом сеансе переписок держатся в памяти и
  показываются сразу, без пустого экрана; сохранённое и свежее дальше только дополняют их на местах.
- Нажатие на уведомление о переписке, которая уже открыта, больше не открывает её заново (не очищает список), а только
  запрашивает свежие сообщения.

### 3.63: по данным дампа — новые сообщения сразу, стикеры, музыка в записях
- **Новые сообщения — сразу, без перезагрузки страницы.** Мессенджер узнаёт о новом сообщении долгим опросом
  (`queuev4…/im…?act=a_check`), а не методом API, поэтому окно чтения видело новое только после перезагрузки страницы
  по таймеру (раз в минуту — от неё список и дёргался). Теперь непустой ответ опроса — сигнал: свежие сообщения
  открытой переписки (или список диалогов) сразу запрашиваются методом API и показываются как обычно.
- **Стикеры и граффити — картинкой** (128 dp, без рамки), а не подписью «[Стикер]»; в списке диалогов — «[Стикер]».
- **Музыка в записях сообществ и людей играет.** В дампе в записях — треки (8 штук на 48 записей), а на своём экране
  страницы они были серой неактивной строкой. Теперь нажатие на трек записи играет его тем же проигрывателем, что музыку
  из переписки: очередь — треки этой записи, уведомление с кнопками, перемотка, фон. Звучащий трек — пауза/продолжить.
- Что ещё видно в дампе (на будущее): в записях есть реакции (не только «нравится»), закладки (`is_favorite`) и
  признак рекламы (`marked_as_ads`, в дампе нет ни одной рекламной); счётчики друзей и заявок (`friends.getCounters`);
  страница сама подписывается на звонки (`queue.subscribe calls_…`). Ссылки вида `audio_api_unavailable.mp3?…` в ответах
  раздела «Музыка» — обычный способ VK отдавать адрес трека, не ошибка.

### 3.64: разбор дампа — данные и логика
Ответы из дампа прогнаны через скрипты страниц (как их видят свои экраны) и сверены с тем, что прислал VK:
стены сообществ и людей — все записи, фото и треки на месте; «Мои треки» и плейлисты разбираются; список сообществ со
счётчиками новых записей — да; ошибок API, кроме ожидаемой `audio.getFullscreenBanner` (104), нет. Найдено и исправлено:
- **Каждая смена раздела была полной загрузкой сайта.** В дампе 49 полных загрузок: вход, главная (71 КБ), пакет
  запросов (54 КБ) — около 130 КБ и заметная пауза на каждый переход между друзьями, сообществами, страницей
  сообщества. Переход «силами страницы» (как нажатие ссылки) раньше был только во время музыки. Теперь — всегда, если
  открыт сайт VK; не сменился адрес за 3 с — полная загрузка, как раньше. Тот же раздел ещё раз — обновление; клипы —
  по-прежнему полной загрузкой.
- **Блокировка статистики мешала счётчику новых записей.** Настройка «Блокировать трекеры» отсекала все
  `statEvents.*` — а на страницах сообществ страница шлёт только их и `open_group`. Через них VK, по всей видимости,
  узнаёт о просмотренных записях: блокировка сводила на нет и вывод увиденных записей на страницу (3.58). Теперь на
  страницах людей, сообществ и записей эти события проходят; на остальных (музыка и т. д.) — блокируются, как раньше.
  Проверить: по следующему отчёту видно, ушло ли «отметка просмотра — запрос statEvents…» и уменьшился ли счётчик.
- **Трек в записи** — в самой записи уже есть адрес потока; теперь он запасной, если `audio.getById` не дал свежий.

### 3.65: по отчёту и дампу 3.64
- **«Прочитано» при открытии переписки больше не теряется.** В отчёте: переписку открыли сразу после запуска, окно
  чтения ещё не успело сделать ни одного запроса к API (нет данных входа) — отметка «прочитано» отбрасывалась с
  предупреждением, и на сайте переписка оставалась непрочитанной. Теперь отметка ждёт первого запроса страницы (до 20 с)
  и уходит сразу после него.
- **Переход в сообщество — нажатием ссылки самой страницы.** В дампе: после открытия сообщества `stats.trackEvents
  open_group` уходит (3.64 — блокировка снята), но с пустыми `track_code` и `source`, а счётчик новых записей
  сообщества в списке («counter» в `catalog.getGroups`) не меняется. Теперь, если в вёрстке страницы есть своя ссылка
  на то же место (сообщество в списке «Мои сообщества» — в том числе по короткому имени), нажимается она: VK сам
  передаёт, откуда пришли, как при обычном нажатии. В журнале — «переход: нажата ссылка самой страницы».
  Проверить по следующему дампу: уменьшился ли `counter` после открытия сообщества.
- **Свой экран, открытый сразу при запуске** (сообщества, музыка), просил данные у ещё не загруженной страницы —
  команда пропадала с предупреждением. Теперь команда «прислать заново» повторяется один раз через 1,5 с.
- Остальное в отчёте чисто: переходы силами страницы работают (ни одного «не состоялся»), полных загрузок при смене
  раздела нет, ошибок нет; несколько подвисаний 100–170 мс при первом создании строк списка диалогов.

### 3.66: уведомление о сообщении не пришло
- **Что было по отчёту.** Фоновая проверка шла каждые ~30 минут до 09:54, а следующая — только в 16:13, когда открыли
  приложение (тогда же и показалось уведомление). Шесть часов система задание не запускала: приложение не исключено из
  оптимизации батареи, им не пользовались — Android переводит его в «редкую» группу и откладывает задания на часы.
  Настоящих push-уведомлений у VK для этого клиента нет, поэтому проверка по расписанию — единственный путь.
- **Страховка будильником.** Раз в период срабатывает будильник «и во сне» (без особых прав). Если периодическая
  проверка опоздала больше чем на 15 минут — ставится срочная проверка (expedited), система запускает её почти сразу.
  Будильники система тоже ограничивает, но мягче: в худшем случае уведомление опоздает примерно на час, а не на полдня.
- **Проверка больше не ждёт «батарея не разряжена»** — при низком заряде она не шла вовсе.
- **Один раз предлагается снять ограничения батареи** (при первом открытии сообщений, если уведомления включены).
  Пункт «Работа в фоне» в настройках теперь сразу открывает системный вопрос для этого приложения. С исключением
  проверка идёт по расписанию надёжно.
- **В журнале** у каждой проверки: периодическая или срочная, сколько минут прошло с прошлой, заряд, сон устройства,
  экономия энергии и группа ожидания; в шапке отчёта — когда была последняя проверка. По следующему отчёту будет видно,
  почему был разрыв.

### 3.67: без перезагрузок страницы, токен — от самой страницы
- **Токен страницы сохраняется вместе со сроком жизни.** Данные входа по-прежнему берутся только из запросов самой
  страницы VK. Теперь они кладутся в хранилище самого сайта (localStorage его адреса) со сроком: из ответа
  `login.vk.ru/?act=web_token` (поле `expires`, в дампе — есть) или из самого токена, если срок в нём зашит (JWT `exp`).
  Новое окно — запуск приложения, окно чтения сообщений — сразу может действовать от имени страницы, не дожидаясь её
  первого запроса. Истёкший токен не используется и удаляется; на ответ «токен устарел» (ошибка 5) — ждём свежий от
  страницы и повторяем один раз. При выходе из аккаунта хранилище сайта очищается, как и раньше.
- **Окно чтения сообщений больше не грузит страницу заново** на каждое действие. Раньше открытие переписки, возврат к
  списку и автообновление раз в минуту — это полная загрузка мессенджера (документ, скрипты, около 360 КБ запросов).
  Теперь:
  - переход в переписку и обратно к списку делает сам мессенджер — нажатием его же ссылки (как человек), данные
    приходят, как обычно, из его запросов, плюс свежая история запросом с его токеном;
  - автообновление — запрос истории или списка диалогов с токеном страницы, без перезагрузки;
  - запасной путь прежний: страница ещё не загружена, скрипта нет, переход не случился за 3,5 с или данных входа
    ещё нет — обычная загрузка. В журнале: «переход без загрузки страницы» / «…не состоялся — загрузка страницы».
  - Явная кнопка «Обновить» по-прежнему перезагружает страницу целиком — на случай, если что-то застряло.

### 3.68: журнал и дамп — недостающие данные
- **Дамп пишет и окно сообщений, и фоновую проверку.** Раньше в дамп попадало только главное окно: истории, диалогов,
  ответов долгого опроса (`a_check`) и сообщений сокета мессенджера (eh.vk.ru) в нём не было. Обезличивание общее
  (`assets/shared/dump_core.js`, подключается вместе с перехватом): токены и подписи — XXX, тексты, имена и контакты —
  «•••(длина)». У каждой записи — поле `window`: «главное», «сообщения» или «фон».
- **Списки в дампе — до 20 элементов** вместо 3: видно счётчики всех сообществ и как сливается история.
- **События токена в журнале** (без самого токена): «взят сохранённый токен, срок — N мин», «сохранённый истёк»,
  «токен из запроса страницы», «страница обновила токен», «устарел (ошибка 5) на методе — ждём свежий»,
  «свежий получен — повтор» / «не дала — не выполнен».
- **Что именно заблокировано:** каждый новый вид заблокированного запроса — один раз в журнал: окно, сервер, путь
  (номера скрыты) и страница. Раньше были только серверы и счётчики.
- **Вывод увиденных записей на страницу сообщества:** итог каждого круга — сколько записей выведено, сколько не нашлось
  и какие отметки (view/seen/mark/track/stat) страница после этого отправила, с количеством. Так будет видно, отмечает
  ли страница просмотр и сбрасывается ли от этого счётчик новых записей.

### 3.69: размер дампа
- **Предел дампа — около 48 МБ вместо 10.** С 3.68 дамп пишут три окна (главное, сообщения, фон), списки — до 20
  элементов: 10 МБ хватало бы на несколько часов, и к моменту выгрузки нужное уже вытеснялось.
- **Хранение частями по 8 МБ**, не больше 6 частей; при заполнении удаляется самая старая часть целиком. Раньше при
  заполнении весь файл читался в память, чтобы оставить новую половину, — с большим пределом это грозило нехваткой
  памяти. Выгрузка — как раньше, одним JSON по порядку записи, потоково.

### 3.70: по отчёту и дампу 3.69
- **Отметка открытия сообщества (`open_group`) больше не блокируется.** Новый журнал заблокированного показал:
  «заблокирован запрос `/method/stats.trackEvents` страница=/club#». Им страница сообщества и шлёт `open_group`; в 3.64
  было разрешено только `statEvents.*`. Заблокированный запрос получал подставной «успех» — поэтому в дампе и казалось,
  что отметка доходит до VK, а счётчик новых записей сообщества не сбрасывался. Теперь `stats.trackEvents` проходит на
  страницах людей, сообществ, записей и в списке «Мои сообщества»; на остальных — блокируется, как раньше.
- **Новые сообщения в открытой переписке — сразу.** Дамп окна сообщений показал, что мессенджер опрашивает
  `api.vk.com/ruim<номер>` (`act=a_check` — в теле запроса), а не только `queuev4…/im…`; события переписки приходят
  именно там. Прежний шаблон этот адрес не узнавал — свежие сообщения ждали автообновления. Теперь узнаёт; события
  «печатает»/«в сети» (коды 60–69, 600–699 — каждые несколько секунд) историю не запрашивают.
- **Переход в сообщество ссылкой страницы так ни разу и не сработал** (в журнале нет «нажата ссылка самой страницы»):
  в вёрстке списка нет ссылки ни на `/club<номер>`, ни на короткое имя. Добавлен журнал: какие ссылки и элементы с
  номером сообщества есть на странице — по нему будет видно, чем список нажимается у VK.
- Остальное по отчёту: фоновая проверка идёт ровно раз в 30 минут (приложение освобождено от ограничений батареи),
  уведомление в 00:25 пришло вовремя; переходы окна сообщений без загрузки страницы работают (ни одного «не
  состоялся»); токен страницы живёт 15 минут — сохранённый успевает пригодиться при быстром повторном открытии.

### 3.71: голосовые как музыка, уведомление, только свои плейлисты
- **Голосовые сообщения играют, как музыка из переписки** (тот же проигрыватель, [ChatMusic]): полоса над полем ввода
  с перемоткой, временем, «назад»/«вперёд»; очередь — все голосовые переписки по порядку, после нажатого сами
  играют следующие (как в VK); кнопки гарнитуры и экрана блокировки. В пузыре голосового полоса теперь тоже
  перематывается пальцем. В полосе и уведомлении: «Голосовое сообщение», автор и время.
- **Уведомление в шторке — всегда**, пока звучит музыка или голосовое из переписки. Раньше оно было только при
  включённом «Фоновом воспроизведении»; настройка теперь решает лишь, играть ли после ухода из переписки.
- **Плейлисты — только свои.** На странице плейлистов VK показывает и чужие — недавно слушанные и добавленные
  (в отчёте: «было 6, стало 13»); они попадали во вкладку. Теперь берутся только плейлисты со своим номером владельца;
  сколько чужих пропущено — в журнале. Сохранённый список очистится от чужих при следующем обновлении.

### 3.72: плейлисты — свои и добавленные; данные из дампа

  занимает место между кнопками и обрезается многоточием; раньше оно лежало по центру поверх всей ширины и наезжало
  на кнопку качества.

### 3.88: поворот экрана для видео
- **Горизонтальный ролик поворачивает экран сам** — во весь экран альбомно, даже если автоповорот в телефоне выключен
  (как в приложении VK); сторона — по датчику. Вертикальный и почти квадратный — как у системы. Решение — по размеру
  кадра, когда ролик готов к показу.
- **Кнопка поворота** в верхней полосе проигрывателя: альбомная ↔ портретная вручную; выбранное держится до закрытия
  (и при смене качества).
- Полный экран встроенного проигрывателя VK и видео на страницах VK (полноэкранный режим главного окна) — тоже
  альбомно; при выходе — снова как у системы.
- Настройка «Поворачивать горизонтальное видео» (включена); выключив её, экран поворачивается только по системе и
  кнопкой.
- Тесты: Kotlin — выбор ориентации по кадру, настройке и ручному выбору.

### 3.89: поворот — по настройке Android
- Все экраны приложения (лента и разделы, сообщения, фото, видео, клипы, настройки) поворачиваются **по настройке
  Android**, как приложения обычно: автоповорот включён — экран следует за телефоном; поворот заблокирован — остаётся,
  как есть, а система предлагает кнопку поворота на панели навигации (`screenOrientation="fullUser"`).
- «Поворачивать горизонтальное видео» теперь **выключено по умолчанию**: видео тоже поворачивается по настройке
  Android. Включив его, горизонтальный ролик открывается альбомно, даже когда поворот заблокирован. Кнопка поворота
  в проигрывателе осталась.
- После полного экрана видео на странице и после проигрывателя — снова по настройке Android.

### 3.90: кнопки видео внизу, фото закрываются смахиванием
- **Проигрыватель видео — своя нижняя полоса** вместо системной: пуск/пауза, полоса перемотки, время
  («1:05 / 12:40»), **качество** и **поворот** — рядом с прокруткой, как в обычных проигрывателях. Сверху остались
  «Закрыть», название и «Страница VK». Обе полосы прячутся и показываются касанием видео; во время игры сами
  прячутся через 3,5 с (пока тянут перемотку — нет). У встроенного проигрывателя VK внизу остаётся только поворот.
- **Фото закрываются смахиванием** вверх или вниз: фото едет за пальцем, фон тускнеет и под ним виден прежний экран;
  отпустили дальше 18 % высоты или бросили быстро — просмотр закрывается, иначе фото возвращается на место.
  Работает у неувеличенного фото и одним пальцем; увеличенное двигается, как раньше; листание вбок — как раньше.
- Тесты: Kotlin — начало смахивания (вертикаль против листания), порог расстояния и броска, затемнение фона.

### 3.91: пересылка — лист с фото получателей
- «Переслать» открывает **лист снизу** вместо голого списка имён:
  - сверху — **что пересылается**: автор и текст (или «Фото · 3», «Видео», «Голосовое сообщение», название вложения);
  - **поиск** по имени (без учёта регистра и «ё»);
  - **получатели с фото** — как в списке диалогов (нет фото — кружок с инициалами), у «Избранного» — закладка;
    под именем — кто это: «Сохранить у себя», «Беседа», «Сообщество», «В сети» (с зелёной точкой) или «Личные
    сообщения»; справа — значок отправки. Нажатие — переслать, как раньше.
- Лист открывается сразу целиком, список не выше 60 % экрана — заголовок и поиск всегда видны.
- Тесты: Kotlin — вид получателя и фото из списка диалогов, поиск, цитата пересылаемого.

### 3.92: по дампу 3.91 — подсказки стикеров, вкладки клипов по ключам
- **Подсказки стикеров по набранному слову**, как в VK: набрали «привет», «спасибо», «ахаха» — над полем ввода ряд
  стикеров; нажатие отправляет стикер и очищает поле. Словарь (`store.getStickersKeywords`, частями по ~1445 групп
  слов со стикерами) страница сама загружает при открытии переписки — приложение его только слушает. Сначала —
  свои недавние стикеры (точно доступны), потом остальные; стикер, который VK не дал отправить (чужой платный набор),
  больше не предлагается. Без учёта регистра, «ё» и знаков в конце («Привет!»); фразы до 40 символов.
- **Вкладки клипов по ключам**: дамп показал ключи `shortVideo.getHeaderTabs` — `rec`, `shops`, `trends`,
  `subscriptions`. Если ряд вкладок в вёрстке не узнан, вкладки ищутся по их подписям («Для вас», «Покупки»,
  «Тренды», «Подписки»); нажимается сама подпись — нажатие всплывает к обработчику страницы.
- Тесты: JS — подсказки (свои первыми, недоступный убран, неизвестное слово — пусто), вкладки по подписям.
  Тест «стикер — картинкой» поймал совпадение имён функций в окне чтения до выпуска.

### 3.93: полоса папок сообщений — сразу при открытии
- Папки приходят от страницы позже списка диалогов (`messages.getDiff`), поэтому полоса «Все · Непрочитанные · …»
  появлялась через секунды после открытия и сдвигала список вниз. Теперь список папок сохраняется и показывается
  сразу вместе с сохранённым списком диалогов; пришли от страницы другие — полоса обновляется.
- **Чёрный пустой экран после настроек**: «Настройки» из меню сообщений закрывали экран сообщений и открывали
  главное окно без загруженной страницы только ради настроек; «Назад» из настроек возвращало в него — заголовок
  «Сообщения» и чёрный экран без списка. Теперь настройки открываются прямо поверх сообщений и «Назад» возвращает к
  списку. Сменили что-то в настройках — экран сообщений пересоздаётся с новыми (тема, обновление, уведомления…);
  вышли из аккаунта или выключили свой экран сообщений — дальше главное окно. А если главное окно всё же окажется без
  страницы после настроек (старый переход, смерть процесса) — открывается стартовый раздел, а не пустота.
- Тесты: Kotlin — сохранение и чтение списка папок, испорченное сохранение — без папок.
