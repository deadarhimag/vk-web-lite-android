# Устойчивость к изменениям VK: план для VkWebLite

Объект: исходники 5.00.03. Документ описывает рекомендуемую архитектуру; перечисленные механизмы не выдаются за уже реализованные. При подготовке плана код приложения не менялся.

Первый реализованный этап: [локальная адаптация 5.00.09](RESILIENCE_5_00_09_RU.md). Автоматическое восстановление и защита операций: [5.00.10](AUTOMATIC_RECOVERY_5_00_10_RU.md). Восстановление окна музыки, ограниченные сетевые повторы и сохранение корректных списков: [5.00.11](AUTOMATIC_STABILITY_5_00_11_RU.md). Остальные пункты ниже остаются архитектурным планом.

## Реалистичная цель

Приложение может автоматически выбирать работающий способ чтения, переживать переименование классов/часть изменений JSON, загружать совместимые правила без нового APK и откатывать неработающее обновление. Полностью неизвестный алгоритм авторизации, новый медиапротокол или изменение доступа к контенту нельзя гарантированно восстановить без внешнего исправления.

Разделить два процесса:

1. Локальная адаптация: уже установленный движок обнаруживает доступные возможности, выбирает один из поддерживаемых путей и проверяет результат.
2. Обновление совместимости: разработчик или проверяемый серверный процесс выпускает новые правила/адаптер; установленное приложение получает их автоматически.

Второй процесс позволяет обойтись без переустановки APK для поддерживаемых изменений, но всё равно требует источника обновлений и сопровождения. Непредусмотренную ранее возможность Kotlin-части придётся добавлять обычным обновлением приложения.

## Что уже есть и что ограничивает устойчивость

- `config/ReaderConfig.kt`: списки селекторов для сообщений централизованы, но зашиты в APK. В селекторах есть широкие запасные варианты вроде textarea/submit: при изменении страницы они могут найти чужую форму.
- `assets/shared/net_tap.js`: общий перехват сетевых ответов и вызовы API страницы. Это хорошая основа чтения структурированных данных, менее зависимого от расположения элементов, но внутренние API VK также могут меняться.
- `assets/vk_lite/50_music.js`: несколько источников треков/потоков; одновременно есть зависимости от `.audio_item`, `data-audio`, `window.audioplayer`, маскировки URL и конкретных страниц.
- `messages/ReaderScript.kt`, `web/PageScripts.kt`: сборка и внедрение скриптов из assets. Ленивая загрузка исходника и проверка наличия `window.__vkReader`/`window.__vkLite` не являются механизмом живого обновления.
- `web/ScriptInjection.kt`: есть повторное внедрение при отсутствии объекта, но нет рукопожатия с версией протокола и проверкой функций.
- `overlay/PageOverlay.kt`: есть повтор, обновление сессии, сохранённые данные и переход на сайт. Это восстановление после сбоя, а не автоматический подбор версии адаптера.
- `web/BridgeListener.kt`: мост уже ограничен доверенными origin и главным фреймом. Эти ограничения нужно сохранить при любых обновлениях адаптеров.

## 1. Ввести единый контракт и независимые адаптеры

Kotlin-экраны должны получать стабильные модели приложения: Track, Playlist, Conversation, Message, Person, Post. Пути полей и классы VK остаются внутри адаптера. У каждого раздела — отдельный набор адаптеров и отдельный статус совместимости; отказ музыки не переключает сообщения на другой непроверенный код.

Контракт адаптера:

- `id`, `version`, совместимая версия мостового протокола, раздел и поддерживаемые семейства страниц;
- `probe`: безопасная проверка признаков страницы/ответов и доступных функций;
- `capabilities`: фактически доступные действия (например, чтение треков работает, поиск потока — нет);
- чтение и нормализация данных;
- проверки результата: валидные идентификаторы, переписка/владелец, структура элементов, допустимые адреса;
- явная остановка: снять обработчики/таймеры и исключить ответы прежнего поколения.

Заменить boolean-проверку внедрения рукопожатием: версия протокола, версия адаптера, поколение страницы и список возможностей. Наличие глобального объекта без нужных методов не считается готовностью. Переход SPA на другой раздел запускает повторную проверку возможностей, а не обязательную полную перезагрузку.

## 2. Использовать несколько уровней получения данных

Общий порядок: структурированные ответы запросов, которые реально выполняет страница → поддерживаемое состояние страницы/плеера → семантические признаки DOM → обычная страница VK. Прямые вызовы известных API допустимы только при действительной авторизации и подтверждённом контракте; это не универсальный обход ограничений сервера.

DOM-правила должны опираться не только на CSS-классы, но и на сочетание роли элемента, подписей доступности, data-атрибутов, структуры, адреса ссылки и границ нужного контейнера. Для чтения допустим выбор наиболее правдоподобного кандидата с проверками. Для отправки, удаления и других действий одного похожего текста кнопки недостаточно.

Изменение ответа API поддерживать явными версиями парсера: известные обёртки, альтернативные имена полей, необязательные добавленные поля. Ограничить глубину обхода и объём входа. Не искать любое вложенное поле `id` или `url` по всему ответу: так плейлист может стать треком, а ссылка рекламы — потоком.

Пустой список различать с отказом парсера. Отсутствие сети, истёкший вход, ограничение доступа, неподходящий тип страницы и изменение схемы — разные состояния. Ошибка авторизации не должна запускать бесконечный перебор селекторов.

## 3. Особенности музыки

Разделить как минимум чтение каталога, получение потока, управление воспроизведением и сохранение файла. У каждой возможности свой probe и своя цепочка резервирования.

Пример цепочки получения потока: поток, возвращённый поддерживаемым ответом → адрес, реально запрошенный плеером для того же трека → подходящий поддерживаемый вариант MP3/HLS → воспроизведение страницей VK. Существующие пути нужно оформить явными стратегиями, а не наращивать общий большой скрипт.

Перед использованием адреса подтвердить принадлежность треку и актуальность операции, origin, вид содержимого и пригодность плейлиста/файла. Быстрая смена треков не должна привязывать старый HLS к новому треку. Истёкшая ссылка требует обновления адреса для той же сущности; это ещё не доказательство изменения разметки. Срок кэша адреса не путать со сроком хранения самого локального MP3.

Если новые правила восстанавливают список, но не получение потоков, показывать список и уже сохранённые файлы, а проигрывание передавать странице. Не выключать всю музыку из-за отказа одной возможности. Если сервер изменил права доступа, шифрование или выдачу контента, адаптер не должен обещать обход этих ограничений.

Аналогично другим разделам: можно оставить чтение переписки при недоступной безопасной отправке, список друзей при недоступном поиске, текст постов при сломанном разборе вложений.

## 4. Автоматически подбирать и проверять путь

Для раздела хранить выбранный адаптер, результат probe и категорию последних ошибок. Структурный отпечаток страницы строить по устойчивым признакам: семейство URL, формы объектов, роли/атрибуты ключевых узлов, доступные методы. Полный хэш HTML или скрипта не подходит: персональные данные и несущественная динамика будут постоянно его менять.

Порядок восстановления:

1. Проверить сеть, вход, правильность страницы и факт загрузки.
2. Проверить здоровье текущей возможности адаптера.
3. При структурной ошибке проверить известный запасной адаптер безопасным чтением.
4. Сравнить нормализованный результат и ограничения, а не только отсутствие исключений.
5. Переключить соответствующую возможность; плохой вариант временно исключить с ограничением повторов.
6. Если надёжного результата нет — сохранить локальные данные и перейти к странице VK для нужного действия.

Один таймаут не означает плохой адаптер. Не обнулять историю, библиотеку и очередь при неудачном распознавании. Перезапуск WebView и смена адаптера должны инвалидировать прежние callback/timer/generation и сохранять неопределённый результат уже начатой отправки.

## 5. Обновлять правила без APK, с откатом

Первый формат — декларативный JSON с версиями селекторов, известных схем и переключателями стратегий. Движок поддерживает фиксированный набор операций; JSON не содержит произвольных eval, URL для выгрузки данных или команд Android.

Пакет описывает модуль, версию правил, минимальный контракт приложения, поддерживаемые семейства страниц и хэши файлов. Подлинность проверяется цифровой подписью по встроенному доверенному ключу. Хэш файла сам по себе подтверждает целостность, а не автора пакета.

Хранить встроенный комплект, последнюю проверенную версию и кандидат. Последовательность: получить → проверить подпись/размер/формат/совместимость → сохранить кандидата → проверить безопасными операциями чтения → активировать атомарно на границе документа/операции → наблюдать → при структурном отказе откатить конкретный модуль. Сетевая ошибка не должна сама запускать откат исправных правил.

Обновление не переключает код посреди отправки, записи файла или сохранения outbox. Последние доверенные правила и встроенный комплект работают без доступности сервера обновлений. Подпись, разрешённые домены, доступ к мосту и подтверждения опасных действий не отключаются конфигурацией.

Если декларативного движка недостаточно, возможен отдельный этап с подписанными JS-адаптерами. Он повышает гибкость, но скрипт выполняется рядом с авторизованной страницей и может видеть её данные. Подпись и доверенный источник обязательны, однако сами по себе не превращают произвольный JS в изолированную безопасную среду. Поэтому начать следует с правил и ограниченных стратегий.

## 6. Безопасная граница самоадаптации

Автоматическое обнаружение разрешать для чтения и проверки. Смена найденной кнопки не должна самостоятельно отправлять тестовое сообщение, удалять запись, ставить реакцию, менять подписку или включать трек для пользователя.

Для изменения данных нужен подтверждённый набор возможностей, явная исходная сущность/получатель, идентификатор операции и проверенный исполнитель. При недостаточной уверенности оставить очередь и открыть нужное действие на сайте. Неподтверждённую отправку не повторять только потому, что новый адаптер «похож на работающий».

Новые диагностические данные — признаки схемы и ошибки, а не токены, cookies, тексты переписок или полные персональные страницы. Передача диагностических снимков наружу — отдельная согласованная функция, а не скрытая часть автообновления.

## 7. Проверки новых правил и автоматизированная подготовка исправлений

Нужен набор обезличенных вариантов DOM/JSON по каждому разделу и поколению страницы. Проверять переименование классов, известные изменения обёрток, добавленные поля, виртуализированный список, переходы SPA, неизвестный язык, истёкший вход и сетевые отказы. Проверять также ложное распознавание: чужая форма не становится композером, соседний трек не получает чужой поток.

К существующим JVM/JS-проверкам добавить браузерные сценарии с воспроизведёнными сетевыми ответами и Android instrumentation для WebView/lifecycle. Тесты с сохранёнными ответами не заменяют проверку действующей страницы. Источники записей очищать от авторизационных и персональных данных до сохранения в репозиторий.

Можно автоматизировать подготовку кандидата на сервере разработки: обнаружить отличие разрешённого обезличенного образца → предложить новый парсер/правила, при необходимости с помощью модели → прогнать тесты → проверить изменение → подписать выпуск. Генерация правки не равна её безопасной публикации. На первом этапе не включать бесконтрольную самогенерацию и исполнение JS на устройстве пользователя.

## Практический порядок внедрения

**Первый выпуск, без сервера обновлений:** единый контракт; рукопожатие версий; независимые capability/probe/health для музыки, сообщений, людей и страниц; реестр встроенных стратегий; классификация отказов; ограниченное резервирование и сохранение локальных данных. Вывести в диагностике выбранный адаптер и доступные возможности.

**Второй выпуск:** единый источник JSON-правил для ReaderConfig и музыкальных DOM/JSON-зависимостей; подписанный загрузчик; кандидат/последняя проверенная/встроенная версии; атомарная активация, откат и ограничения обновления во время операций. Для автоматической доставки нужен выбранный HTTPS-источник и процесс подписи релизов; их в текущем проекте ещё нет.

**Третий выпуск:** расширенные обезличенные fixtures, браузерные/устройственные проверки, автоматическое обнаружение изменений и подготовка кандидатов. После устойчивой работы — оценить необходимость удалённых JS-адаптеров.

Критерии приёмки: известное изменение классов восстанавливается без APK; неизвестная схема не очищает данные; сломанное музыкальное управление не ломает каталог; плохой подписанный совместимый пакет откатывается; поддельный и несовместимый пакеты не активируются; отсутствие сервера не мешает встроенному комплекту; новая разметка не провоцирует ни одной самопроизвольной отправки.

## Первичные справочные источники

- Android Developers, [WebView — Native bridges](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges): риски выполнения доверенного/недоверенного кода рядом с нативным мостом, проверки origin и HTTPS.
- Playwright, [Mock APIs](https://playwright.dev/docs/mock): воспроизведение ответов и HAR для браузерных проверок. Авторизационные записи нельзя коммитить без предварительной очистки.

Эти источники подтверждают возможности инструментов и ограничения доверия; предложенные модули, порядок внедрения и правила автоматического отката — проектное решение для VkWebLite, а не готовая функция Android или VK.
