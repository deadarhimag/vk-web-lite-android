## 1. P1 — отмена не убирает уже прикреплённые файлы из композера страницы

Места: `app/src/main/assets/vk_reader.js:2146` (`cancelTransfer`), `:2297` (передача файлов в input); `app/src/main/java/com/example/vkweb/messages/AttachmentComposer.kt:187`; `MessagesActivity.kt:1022` относительно той же папки messages.

`cancelTransfer` сбрасывает staging, флаг и таймеры приложения, но после присваивания `input.files` и события `change` файлы уже находятся у композера VK. Отмена не очищает input, не удаляет вложения из состояния страницы и не прерывает начатую страницей загрузку. При поздней отмене также остаётся введённая подпись.

Сценарий: вложение передано странице → загрузка/отправка завершается ошибкой или таймаутом → `AttachmentComposer.fail()` отменяет передачу и снимает busy → `onBusyChanged(false)` немедленно разрешает текстовой очереди продолжить отправку через тот же композер. В нём могут остаться файлы отменённой операции. Другой путь — убрать выбранные файлы в интерфейсе приложения и отправить обычный текст. Следующее нажатие может отправить также отменённое вложение; повтор передачи может добавить дубликат.

Подтверждение: настоящие функции `attachAndSend`, `cancelTransfer`, `sendMessage` в существующем управляемом DOM: после отмены кликов 0, но `input.files.length == 1` и подпись осталась; последующий обычный `sendMessage` нажимает кнопку при всё ещё заполненном файловом input. Это подтверждает отсутствие очистки на стороне приложения; точное поведение внутреннего upload-state реального VK требует проверки на устройстве.

Исправление: после передачи файлов странице считать композер загрязнённым до подтверждённой очистки. При отмене удалить вложения средствами страницы либо пересоздать/перезагрузить её; до этого запретить обычной очереди использовать композер. Простого `input.value = ''` недостаточно для уже принятого страницей вложения.

## 2. P1 — одно серверное сообщение может подтвердить две записи очереди

Места: `app/src/main/java/com/example/vkweb/outbox/OutboxLogic.kt:103`, `:127`; источник события — `app/src/main/assets/vk_reader.js:1623`.

В очереди разрешено отправлять следующее сообщение при наличии предыдущего UNCONFIRMED. Если тексты одинаковы, `deliveredByServer` выбирает первую запись SENDING **или UNCONFIRMED** с подходящим текстом, независимо от того, на какой запрос пришёл ответ. Затем `reconcile` использует ту же серверную запись для оставшегося сообщения: список использованных идентификаторов существует только внутри одного вызова reconcile и не связан с обработанным ответом отправки.

Воспроизведение на production Kotlin: старая фактически неотправленная запись `old` (UNCONFIRMED, текст `ok`), новая `current` (SENDING, тот же текст). Единственный успешный ответ отправки новой записи удаляет `old`; история с единственным `c100: ok` затем удаляет `current`. Очередь пуста, хотя сервер получил только одно из двух сообщений. Реальный путь появления старой неотправленной UNCONFIRMED описан в замечании 3.

В предыдущем ревью корреляция упоминалась как архитектурная рекомендация. Здесь подтверждено конкретное ошибочное поведение, поэтому это дефект корректности, а не только улучшение протокола.

Исправление: сохранять и передавать идентификатор отправки до ответа; подтверждать конкретный itemId, сохранять возвращённый сервером messageId/cmid и учитывать уже использованные подтверждения при последующей сверке. Одного выбора SENDING перед UNCONFIRMED недостаточно: старое сообщение всё ещё может ошибочно подтвердиться той же записью истории.

## 3. P2 — отменённая до отправки фоновая команда остаётся SENDING

Места: `app/src/main/java/com/example/vkweb/sync/HeadlessSync.kt:92`, `:98`, `:360`; `SyncMachine.kt:98` и `onStepTimeout` в том же пакете.

SyncMachine переводит сообщение в SENDING до подтверждения дисковой записи. HeadlessSync правильно ждёт `whenPersisted`, но уже запускает таймаут шага 30 секунд. Если сохранение задержалось, таймаут переключает шаг/завершает работу. Поздний callback блокируется проверкой finished/commandGeneration. Аналогично отмена задания во время ожидания записи не вызывает отправку. При этом ни один из этих путей не возвращает **ещё не отправленную** запись в QUEUED.

Сохранение может ждать другие задачи общего последовательного OfflineStore; остановка задания системой возможна и до истечения таймаута. Запись остаётся SENDING, а после восстановления процесса становится UNCONFIRMED. Автоматический повтор для неё запрещён: пользователь должен вручную повторять сообщение, которое приложение точно не пыталось отправить.

Подтверждение: production SyncMachine с управляемым OutboxAccess выдаёт Send, затем при таймауте до dispatch — Finish, оставляя SENDING. Production `OutboxLogic.restore` превращает её в UNCONFIRMED. Подавление позднего dispatch подтверждено чтением HeadlessSync; Android JobService в этом воспроизведении не запускался.

Исправление: отдельно отслеживать «ожидает commit» и «команда действительно передана странице». При таймауте, отмене и неуспешном commit безопасно возвращать в QUEUED только команды, не дошедшие до dispatch. Реально отправленные оставлять сомнительными.

## 4. P2 — зависшая отправка голосового блокирует обычную очередь без срока

Места: `app/src/main/assets/vk_reader.js:2069`, `:2090`; `app/src/main/assets/shared/net_tap.js:315`; `app/src/main/java/com/example/vkweb/messages/MessagesActivity.kt:1753`, `:324`.

При отправке выставляется `voiceSending = true`. У цепочки API → upload fetch → docs.save → messages.send нет таймаута приложения или AbortController. У общего `NetTap.api` таймаута запроса также нет; ожидание обновления авторизации ограничено, но оно не ограничивает сам HTTP-запрос. Таймер AttachmentComposer к голосовому не применяется.

Если хотя бы один запрос остаётся pending, не приходит ни успех, ни ошибка, `voiceSending` не сбрасывается. `Host.isChatOpen` из-за этого возвращает false, и текстовая очередь текущей переписки перестаёт отправляться; микрофон также не возвращается до смены экрана/переписки. Файл исходной записи уже удалён AttachmentSender после staging, отдельного пути повторить запись нет.

Подтверждение: настоящая JS-функция sendVoice с управляемым API, который не завершает запрос: спустя 10 минут виртуального времени нет voiceSent, операция остаётся активной. Блокировка очереди следует из Kotlin-условия isChatOpen. Это отсутствие гарантированной границы ожидания; длительность системного сетевого таймаута на конкретном устройстве не измерялась.

Исправление: общий таймаут операции с отменой fetch/проверкой operationId, обязательным уведомлением Kotlin и сбросом busy. При неопределённом результате messages.send не сообщать «точно не ушло» и не повторять автоматически.

Из корня проекта:

```powershell
.\.review-tools\run-checks.ps1
.\.review-tools\run-second-review.ps1
```

Отдельно JS без npm-зависимостей: `node re-review-checks.cjs`.

Исходники воспроизведений: `re-review-checks.cjs`, `.review-tools/SecondReviewRepro.kt`. Kotlin-воспроизведения используют production-классы из tests.jar предыдущего шага; модель Android/хранилища остаётся изолированной. При изменении production-кода сначала пересобрать tests.jar первой командой.
