# Автоматическое восстановление 5.00.10

Сборка 218. Новых настроек, разрешений, кнопок и подтверждений для этих механизмов нет. Они работают внутри существующего кэширования и чтения страниц. Пользователь продолжает обычную работу с приложением.

## Обновление истёкшего адреса музыки

Если адрес истёк, пока задача ждала в очереди, запрос по нему не начинается. Если сервер звука/манифеста/сегмента вернул HTTP 401, 403, 404 или 410, приложение допускает один автоматический поиск свежего адреса того же трека.

Временные данные неудачной попытки очищаются, задача передаётся существующему скрытому окну музыки. Его документ перезагружается, чтобы VK не продолжил использовать адрес из памяти старого плеера. Очередь поиска сохраняется и приоритет получает восстанавливаемый трек. В JS адрес этого ID принудительно исключается из памяти потоков. Свежий результат передаётся обратно загрузчику, после чего действует прежнее получение MP3/HLS/DASH, преобразование в MP3 и публикация файла.

Итог исходной задачи сообщается после окончательного результата; первый отказ сам по себе не завершает её ошибкой. Треки из плейлиста сохраняют страницу исходного списка; при неизвестном контексте используется обычная страница музыки.

Защита от повторов:

- Разрешён один цикл обновления адреса на исходную загрузку. Повторный отказ завершает её.
- HTTP 429/5xx, ошибка преобразования и произвольный IOException не запускают этот механизм.
- Пока адрес конкретного трека обновляется, повторные фоновые события не создают ещё один поиск.
- Восстановленная автоматическая задача сохраняет свой автоматический статус; существующий лимит неудач за процесс не сбрасывается. Неудача самого поиска URL тоже учитывается.
- Блокировка обновляемого ID освобождается условно, по уникальному номеру восстановления, поколению кэша и отмены. Поздняя очистка старой задачи не может освободить блокировку новой.
- Если MP3 уже существует, повторное скачивание и поиск адреса не требуются.

Очередь HTTP не ждёт скрытый WebView синхронно: остальные загрузки могут выполняться, пока идёт новый поиск. Это исключает взаимное ожидание поиска потока и последовательного загрузчика.

## Поколения операций и отмена

Каждая порция поиска в скрытом окне получает operation. JS возвращает его в musicStreams. Нативная сторона принимает результат только для запрошенного ID текущей порции и только один раз. Старый ответ не может завершить новый поиск того же трека; повторное/постороннее сообщение не продлевает таймер ожидания.

При перезапуске поиска старые задачи чтения возвращаются в очередь с прежними наблюдателями. Несколько просьб, ожидающих один поиск трека, получают один установленный исход, вместо преждевременного «уже был».

Все ожидающие задания скрытого окна, включая обычные, сохраняют поколения кэша и отмены. После очистки, выхода из аккаунта или остановки очереди они не получают новую действующую метку при позднем ответе. Эти задания отменяются; восстановление не воссоздаёт очищенный кэш.

Существующее правило остановки сохраняется: уже начатая обычная загрузка может завершиться; автоматический повтор после остановки не запускается.

## Защита внутри страницы

Генерация воспроизведения связывает нажатие, сетевой запрос манифеста и отложенную привязку. Ответ/таймер старого трека отбрасывается после следующего включения. Проверка через 1,5/4 секунды не может повторно нажать строку более нового трека. Запланированный шаг старого поиска не выполняет шаг нового поиска.

Поколение SPA теперь обновляется при реальных pushState/replaceState/popstate. Перехват сохраняет аргументы, this и результат исходного вызова и сам не инициирует переход. Запоздавший API-ответ отвергается даже после перехода A → B → A на тот же URL. Навигационные документы и глобальные потоки сохраняют свои отдельные правила обработки.

Действия записи — отправка сообщений, удаление, реакции и подобные операции — новых автоматических повторов не получили. Настройки и пользовательские сценарии интерфейса не расширялись.

## Проверки

- 125 изолированных JVM-тестов: предыдущие 114 и 11 новых проверок политики восстановления/идентичности порции. Три JSON-теста явно исключены.
- 18 управляемых проверок очереди: в тестовую границу извлекаются настоящий cache(), finishRecovery() и класс Job из текущих исходников, затем компилируются с настоящими моделями и CacheBatch. Проверены единый результат, очистка до передачи задачи, истечение в очереди, отмена/очистка, ограничение повторов, повторные фоновые события, сохранение лимита неудач, освобождение по уникальному номеру и общие наблюдатели. Границы HTTP/публикации моделируются; это не проверка настоящего FFmpeg или Android WebView.
- Три проверки настоящих MusicTrack/MusicDownload прошли; JSON-типы служат только для компиляции.
- Синтаксис 459 Kotlin-файлов проверен.
- 100 JS-проверок прошли: в том числе старые ответы после смены трека, устаревшие шаги/таймеры, принудительный поиск, отмена и переход A → B → A. Мутационный корпус содержит 12 вариантов переименованной/частично изменённой DOM-строки, 10 вариантов JSON-обёрток/порядка полей и пять удалений обязательного поля идентичности; эти 27 входов входят в три именованные проверки.

Полная Android-сборка и Lint здесь недоступны: отсутствуют JDK 17 и Android SDK. jsdom-набор не запускался из-за отсутствия зависимости. Успешное обновление настоящего истёкшего URL в VK и полный цикл MP3 на Android ещё не проверены установленной 5.00.10. Код восстановления и тесты не гарантируют доступ к удалённому/недоступному треку: после ограниченной попытки остаётся прежний штатный результат неудачи.

Данные аккаунта и локальную музыку для обновления очищать не требуется. Диагностический журнал использует существующую настройку; работа восстановления от включённости сбора дампа не зависит.
