## Найденный пробел и правка 5.00.07 (215)

`shared/net_tap.js` передавал подписчикам fetch только с MIME, похожим на json/text/javascript/mpegurl. XHR обрабатывал только текст и JSON; ArrayBuffer/Blob не декодировались. Поэтому настоящий HLS, выданный как application/octet-stream или бинарный XHR, оставался невидимым для существующего распознавателя #EXTM3U.

Это подтверждённое ограничение кода. **Что именно такой ответ приходит в этом эпизоде, текущие файлы не доказывают.** Правка закрывает этот путь и добавляет сведения, необходимые для проверки других вариантов.

В 5.00.07:

- Только подписчик музыки явно запрашивает ограниченную проверку бинарного ответа. Остальные потребители ответов, включая дамп API и сообщения, по-прежнему получают текст своим обычным путём.
- Копия бинарного fetch читается порциями, проверяется сигнатура #EXTM3U. Полное чтение допускается только для HLS в пределах 256 КиБ; для прочего бинарного медиа проверяется начало и чтение копии отменяется. При заранее указанной большой длине копия вообще не создаётся. Максимальное ожидание инспекции — 5 секунд; исходный ответ и Promise страницы сохраняются.
- HLS из XHR ArrayBuffer/Blob декодируется только в пределах 256 КиБ и передаётся подписчику после проверки сигнатуры. Ответ, который получает страница, не меняется.
- Новые поля диагностических снимков: последние 16 ответов аудиосерверов с HTTP-статусом, MIME, размером из заголовка, способом получения и responseType; отдельно классификация тела hls/dash/mp4/other/limit/unreadable/timeout и накопленные счётчики этих категорий. Полные адреса, параметры запроса и тела в эти поля не сохраняются.
- DASH/MP4 не выдаются за HLS и не направляются в загрузчик HLS. Алгоритм привязки потока к треку не менялся: запрошенный ID сам по себе не становится подтверждением содержимого.
