# Ревью VkWebLite 5.00.00

Дата: 23 октября 2026. Исходник: `Downloads/VkWebLite-5_00_00.zip`, версия 5.00.00, versionCode 208.

## Результат

Найдено 13 замечаний: 4 с приоритетом P1 и 9 с приоритетом P2. Главные риски: отправка в другую переписку после смены экрана, потеря очереди при завершении процесса, отсутствие восстановления скрытых WebView и блокировка интерфейса длительными операциями кэша.

P1 — исправить до следующего релиза; P2 — включить в ближайший цикл исправлений. Это приоритет исправления, а не утверждение, что ошибка возникает у каждого пользователя.

Проверены структура, конфигурация сборки и CI, manifest, границы доверия WebView, каналы Kotlin ↔ JS, хранение и очистка данных, очередь сообщений, фоновая синхронизация, передача файлов и голосовых, загрузка музыки/HLS, кэш изображений и ряд правил слияния/UI. В проекте 307 production-файлов Kotlin и 136 файлов Kotlin-тестов. Углублённый ручной разбор сосредоточен на перечисленных подсистемах; наличие тестового файла не считается доказательством корректности подсистемы.

Исходники приложения не изменялись. Добавлен независимый `review-checks.cjs`. Проверки извлекают настоящие JS-функции из исходника и запускают их с минимальными заглушками; это не интеграционный тест настоящей страницы VK.

## Замечания

### 1. P1 — отмена вложений не отменяет уже начатую JS-отправку

Места: `messages/AttachmentSender.kt:36,69`, `messages/AttachmentComposer.kt:193`, `assets/vk_reader.js:2181,2194,2209,2215`. Пути Kotlin здесь и далее относительно `app/src/main/java/com/example/vkweb/`.

`cancel()` меняет только Kotlin-поколение передачи. После `attachAndSend()` в странице продолжают жить `withFileInput()` и `waitSendReady()`. Они не привязаны ни к поколению, ни к peerId. При SPA-переходе A → B отложенный callback вызывает `sendMessage()` через текущий композер B. Возможна отправка подписи/доступных композеру вложений в другую переписку. Кроме того, проверка поколения перед `main.post` не защищает от отмены между постановкой callback и его выполнением.

Подтверждение: `node review-checks.cjs` воспроизводит выполнение отправки через B после запуска для A. Поведение настоящего DOM при переходе нужно дополнительно проверить на устройстве.

Исправление: передавать `operationId + peerId` во все стадии; добавить JS-команду отмены, снимать её таймеры и проверять peer/поколение непосредственно перед изменением композера и перед нажатием «Отправить». Повторить проверку поколения внутри Kotlin `main.post`. Таймаут в `AttachmentComposer.fail()` также должен отменять операцию.

### 2. P1 — завершение записи голосового может выбрать нового получателя

Места: `messages/VoiceComposer.kt:141,152,163`, `messages/MessagesActivity.kt:1269,1720,1736`.

`finish(send=true)` сразу снимает `isRecording`, но результат `stopAsync` приходит позже. При смене переписки `release()` уже ничего не отменяет: запись формально закончилась. Callback проверяет только `destroyed`, затем `MessagesActivity.sendVoice()` читает актуальный `currentPeer`. Если между этими событиями открыть B, запись, законченная в A, будет адресована B.

Статическое подтверждение: получатель не захватывается ни в результате записи, ни в callback. На Android следует воспроизвести задержкой `stopAsync`.

Исправление: захватывать peerId и поколение операции до асинхронной остановки; инвалидировать ожидающий результат при смене переписки. Результат старого поколения удалять без отправки.

### 3. P1 — принятие сообщения в очередь не означает его сохранение

Места: `outbox/Outbox.kt:57`, `offline/OfflineStore.kt:238`, `sync/ReplyReceiver.kt:43,50`, `messages/ChatOutboxDriver.kt:105`.

`Outbox.update()` меняет память, ставит запись в executor и возвращается без подтверждения диска. `ReplyReceiver` после этого вызывает `pending.finish()`: время жизни приёмника больше не защищает запись. При завершении процесса до выполнения IO новый ответ исчезает. В открытом чате UI также может уже очистить ввод. Обратное окно: сообщение отправлено, но удаление из очереди ещё не записано — после перезапуска восстанавливается старое состояние.

`fsync` внутри `write()` помогает только после фактического начала записи и не закрывает окно между постановкой задачи и её выполнением. Ошибки сохранения доступны лишь журналу.

Исправление: отдельное надёжное хранилище очереди с результатом транзакции; подтверждать приём сообщения и завершать `goAsync()` после успешного commit. Запускать внешнюю отправку после сохранения состояния отправки. Передавать ошибку сохранения в UI. Практический вариант — Room/SQLite с транзакциями и постоянным идентификатором отправки.

### 4. P1 — скрытые WebView не обрабатывают потерю renderer

Места: `messages/ReaderPageClient.kt:25`, `media/MusicCacheWorker.kt:221`. Обработчик существует только в `web/VkWebViewClient.kt:193`.

У окна сообщений, фонового чтения и окна кэша отсутствует `onRenderProcessGone`. Поэтому предусмотренное для главного окна восстановление не распространяется на остальные окна. При падении/выгрузке renderer нет безопасного уничтожения и восстановления затронутого скрытого WebView; стандартное поведение может завершить процесс приложения. Общий renderer может затронуть несколько окон одновременно.

Исправление: обработать событие у каждого клиента, удалить повреждённое окно из иерархии, освободить его и пересоздать при необходимости. Для фоновой работы завершить/перепоставить задание, для неопределённой отправки сохранить безопасное состояние. Проверка на эмуляторе: падение renderer отдельно в сообщениях и при кэшировании, включая одновременные окна.

### 5. P2 — несколько выбранных файлов могут незаметно превратиться в один

Место: `assets/vk_reader.js:2202`; завершение: `messages/AttachmentComposer.kt:178`.

При `input.multiple == false` используется `files.slice(0, 1)`. Остальные выбранные файлы отбрасываются без ошибки. Затем успешное нажатие очищает весь список файлов в приложении. Пользователь может считать отправленными все вложения.

Подтверждено выполнением настоящей `attachAndSend` с тремя файлами и одиночным input: в input передан один файл.

Исправление: выбирать подходящий multiple-input, реализовать последовательное прикрепление либо явно отказать в операции до отправки. Успех должен учитывать количество действительно прикреплённых файлов.

### 6. P2 — коллизия String.hashCode приводит к пропуску изменённых данных

Место: `offline/OfflineStore.kt:241,249`.

После первой записи совпадение 32-битного `hashCode()` считается равенством содержимого. Строки `[{"text":"Aa"}]` и `[{"text":"BB"}]` различаются, но обе имеют Java hashCode `368381991`. Замена текста в остальном идентичном JSON способна оставить на диске прежнюю версию. Аналогично затрагиваются очередь, история и прочие записи через `write()`.

Подтверждение коллизии включено в `review-checks.cjs` как воспроизведение алгоритма Java String.hashCode, а не запуск Kotlin-хранилища.

Исправление: хэш использовать как предварительную проверку с последующим сравнением содержимого либо хранить достаточно стойкий digest. Для очереди лучше исключить эту оптимизацию до появления измеренной необходимости.

### 7. P2 — fallback замены файла может удалить последнюю исправную копию

Место: `offline/OfflineStore.kt:263,264`.

Если первый `renameTo` не удался, код удаляет старый файл и повторяет rename без проверки результата. При втором отказе старые данные потеряны, новые остаются в `.tmp`, который загрузчик не читает. Несмотря на это, обновляется `lastWritten` и журнал сообщает «сохранено».

Исправление: не удалять исправный оригинал до гарантированной замены; использовать `AtomicFile` либо атомарное перемещение с проверкой результата и безопасной резервной копией. Добавить восстановление после незавершённой записи и fault injection на отказ переименования.

### 8. P2 — очистка картинок допускает восстановление удалённого кэша

Место: `offline/ImageCache.kt:247,267,345`.

`clear()` очищает память и удаляет готовые файлы, но не отменяет задания network/background, не меняет поколение загрузок и специально оставляет `.part`. Уже идущая загрузка после очистки переименует `.part` в готовый файл; отложенный callback снова заполнит memory-cache. Это нарушает смысл очистки и особенно нежелательно при выходе из аккаунта, который вызывает `Storage.clearAll()`.

Исправление: поколение кэша, проверяемое перед публикацией файла и доставкой bitmap; отмена устаревших заданий, удаление их временных файлов. `done` должен означать установленную границу очистки, после которой старые результаты не принимаются.

### 9. P2 — объединение входящих сообщений смешивает разные переписки

Место: `messages/ReaderChannel.kt:208–215`.

Ключ pending — только тип сообщения. Если до flush приходят `History(A)` и `History(B)`, останется только B. Разные переписки — независимые данные, а не две версии одного снимка. Кроме того, каждый пакет переносит общий flush на 180 мс: поток обновлений чаще этого интервала может откладывать доставку неограниченно долго.

Исправление: ключ `(type, peerId)` для истории; отдельное правило для диалогов. Ставить flush при первом элементе пачки или ограничить максимальное ожидание. События завершения операций доставлять без такого объединения. Проверить A+B за один интервал и непрерывный поток длительностью несколько секунд.

### 10. P2 — повтор фоновой работы ждёт самую позднюю попытку в очереди

Место: `sync/MessageSyncService.kt:111`.

После завершения берётся `maxOfOrNull(retryAt - now)` по всем QUEUED. При готовом сообщении A и сообщении B с backoff в 60 секунд A тоже задерживается до B. Будущие запланированные сообщения также участвуют в этом расчёте, хотя будильник для них отдельный.

Исправление: рассчитывать ближайшее время допустимой работы по первым доступным сообщениям каждой переписки с учётом порядка и sendAt. Сохранить ограничение частоты фоновых запусков, но не привязывать весь процесс к самому позднему элементу.

### 11. P2 — общий лимит вложений не проверяется по фактически прочитанным байтам

Места: `messages/AttachmentPolicy.kt:26`, `messages/AttachmentSender.kt:31,88`.

Неизвестные размеры исключаются из суммы. При чтении применяется только ограничение одного файла. Например, десять потоков с неизвестным размером по 12 МБ каждый пройдут проверку, несмотря на MAX_TOTAL_BYTES = 24 МБ. Все части затем удерживаются в JS `staged` как base64, а сборка создаёт дополнительные Uint8Array/File. На устройстве с малой памятью это создаёт риск OOM.

Исправление: считать общий объём по мере чтения всех файлов; прерывать передачу до превышения лимита и чистить JS staging. Для снижения пиков памяти читать файл потоком вместо ByteArrayOutputStream → toByteArray и освобождать принятые части после сборки.

### 12. P2 — лимит истории ограничивает выдачу, но не занимаемую память

Места: `assets/vk_reader.js:655,663,775,793,1156`.

`history` хранит bucket каждого посещённого peer. При поступлении сообщений bucket пополняется. `slice(-MAX_HISTORY)` ограничивает только сериализуемый ответ; старые записи в bucket не удаляются, а число peer не ограничено. При длительной SPA-сессии растут память, стоимость сортировки и паузы GC.

Исправление: ограничивать bucket при добавлении данных и применять LRU к перепискам. Оставлять открытый peer и небольшой набор недавних/предзагруженных. Лимит должен распространяться на реально хранимые данные, включая provisional-записи.

### 13. P2 — фоновые операции музыки способны блокировать главный поток через общий lock

Места: `media/MusicCache.kt:103,106,356,362,364,417`; `media/MusicDownloadStarter.kt:58`; вызывающая сторона: `overlay/MusicOverlay.kt:148,208`.

`rescan()` держит lock во время миграций, копирования файлов и запросов MediaStore; `publish()` держит его во время записи готового MP3. Между тем `cache()` вызывается из UI и синхронно обращается к `currentGeneration()`, который требует тот же lock. Поэтому вынесенная в фон файловая работа всё равно может заморозить UI на время длительного копирования/миграции.

Исправление: считывать поколение через AtomicLong/volatile; файловую работу выполнять вне короткой секции публикации индекса. Для миграции и публикации сохранить отдельную сериализацию и проверку поколения перед фиксацией. Проверить большим кэшем при одновременном нажатии «Кэшировать».

## Дополнительные улучшения эффективности и устойчивости

1. **Ограничить очереди executor.** `Background.kt` создаёт неограниченный LinkedBlockingQueue. Для UI-картинок и снимков страниц полезны удаление устаревших задач, дедупликация по ключу и предел очереди. Политика очереди сообщений должна быть отдельной: бизнес-операции нельзя молча отбрасывать.
2. **Не делать fsync для каждого промежуточного снимка.** После исправления надёжного хранения outbox можно объединять ожидающие записи истории/списков по имени файла. Очередь отправки требует подтверждения commit; обычному кэшу достаточно последнего снимка. Сейчас серию снимков сериализуют и сбрасывают на диск по очереди.
3. **Добавить корреляцию команд и ответов.** `OutboxLogic.deliveredByServer()` сопоставляет по тексту и peer, а `randomIdOf()` сворачивает UUID в 31 бит. Лучше сохранять идентификатор запроса/отправки как поле outbox и возвращать его в delivered/sent. Это снимет неоднозначность одинаковых текстов и уменьшит зависимость от состояния текущей страницы. Это отдельное улучшение протокола, не доказательство произошедшей потери сообщения.
4. **Усилить CI.** В `.github/workflows/build.yml:48` lint не блокирует сборку; тестируется debug. Сделать новые ошибки lint блокирующими относительно baseline и проверять release с R8. Сквозные сценарии WebView, lifecycle и фоновых заданий требуют instrumentation-тестов.
5. **Проверить выход из аккаунта как единую операцию.** В `SettingsFragment.kt:338` удаление cookies асинхронное, callback не используется, очистка остальных хранилищ также не ожидается. Перед сообщением об окончании полезен единый барьер остановки операций, очистки и обновления окон. Отдельно проверить активное кэширование и быстрый повторный вход; конкретный межаккаунтный сценарий в этом аудите на устройстве не воспроизводился.
6. **Измерять результат оптимизаций.** Полезные показатели: максимальное время ожидания main-thread lock, размер очередей executor, число хранимых JS-сообщений/peer, объём сериализации и fsync, память renderer после длительной навигации. Существующие AppLog/FreezeWatch дают основу для таких измерений.

## Порядок исправлений и приёмка

1. Закрыть отправку в другой peer: вложения и голосовые; поколения операций, явная отмена и корреляция ответов.
2. Сделать outbox устойчивым к завершению процесса, ошибкам записи и отказам замены файлов.
3. Обработать renderer всех WebView и устранить длительные блокировки главного потока.
4. Исправить очистку кэшей, обработку пачек, retry и реальные ограничения памяти/размеров.
5. Запустить штатные JS/Kotlin-тесты, lint и release-сборку в JDK 17 + Android SDK; затем instrumentation на API 26 и современных API.

Обязательные сценарии приёмки: A → B во время передачи/остановки записи; 3 файла в input без multiple; неизвестные размеры >24 МБ суммарно; завершение процесса сразу после ответа из уведомления; отказ rename; очистка/выход при активной загрузке; падение renderer при двух окнах; две истории за одну пачку; непрерывные обновления без голодания; готовое сообщение рядом с backoff другого peer; несколько часов навигации без неограниченного роста памяти.
